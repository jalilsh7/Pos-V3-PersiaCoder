# ممیزی واقعی سورس 3Food POS برای مهاجرت به PHP و MySQL

> **گزارش تاریخی:** این سند وضعیت snapshot اولیه در 2026-11-16 را توصیف می‌کند و معماری فعلی شاخه پاک‌سازی نیست. لایه‌ی فعال cPanel اکنون React/Vite SPA + PHP API + MySQL است؛ کدهای Better Auth، PGLite/PostgreSQL و اتصال‌های Grok از شاخه `cleanup/remove-grok-dependencies` حذف شده‌اند. برای وضعیت جاری به `README.md` و `AI_HANDOFF_FA.md` مراجعه کنید.

## نتیجه اجرایی

سورس فعلی یک برنامه React 19 + Vite + TanStack Start است که سمت سرور آن با Node.js/Nitro اجرا می‌شود. این پروژه در وضعیت فعلی روی هاست PHP-only قابل استقرار مستقیم نیست. صرفاً تغییر تنظیمات دیتابیس یا حذف چند فایل Grok کافی نیست؛ لازم است لایه سرور و ذخیره‌سازی به PHP/MySQL منتقل و رابط React به فایل‌های استاتیک تبدیل شود.

در این مرحله سورس و ساختار آن بررسی شده و گزارش فنی تولید شده است. هنوز منطق اجرایی برنامه تغییر نکرده و نسخه قابل انتشار PHP ساخته نشده است.

## ساختار و فناوری‌های فعلی

- رابط: React 19، TypeScript، Tailwind CSS 4، Zustand، Recharts و Lucide.
- چارچوب اجرا: Vite 8، TanStack Router/Start و Nitro 3 beta.
- هدف انتشار فعلی: Nitro با preset برابر `vercel` در `vite.config.ts`.
- دیتابیس فعلی: PostgreSQL از طریق `pg` یا PGlite در حافظه؛ نه MySQL.
- احراز هویت: Better Auth با اتصال‌های مخصوص Grok؛ ورود محلی با نام کاربری/رمز عبور فعال نیست.
- تنها API کاربردی فعلی: `src/routes/api/sms.ts`؛ APIهای صندوق و دیتابیس مرکزی وجود ندارند.
- ذخیره‌سازی POS: Zustand persist با کلید `grillcash-v1` در فضای ذخیره‌سازی مرورگر.

## موانع قطعی برای استقلال

### 1. اجرای سرور به Node.js وابسته است
`package.json`، `vite.config.ts`، `startup.sh` و routeهای TanStack Start برای اجرای Node/Nitro نوشته شده‌اند. خروجی `.vercel/output` نیز artefact انتشار Vercel است. روی هاست PHP-only، اجرای SSR و route handlers فعلی ممکن نیست.

**راهکار:** Build رابط React در محیط توسعه/CI و انتقال فایل‌های خروجی استاتیک به هاست؛ جایگزینی route handlers با APIهای PHP.

### 2. دیتابیس با هاست MySQL سازگار نیست
`src/lib/db.ts` از `pg` و PostgreSQL استفاده می‌کند و در نبود `DATABASE_URL` به PGlite حافظه‌ای برمی‌گردد. `scripts/migrate.mjs` نیز migrationهای PostgreSQL را با Node اجرا می‌کند. در `migrations/` هیچ schema عملیاتی POS در سطح ریشه وجود ندارد؛ فایل auth در زیرپوشه است.

**راهکار:** طراحی schema جدید MySQL/InnoDB و مهاجرت‌گر PHP با PDO و تراکنش‌ها. در production هیچ fallback حافظه‌ای مجاز نیست.

### 3. ورود و نقش‌ها برای استفاده واقعی امن نیستند
- `src/lib/auth/server.ts` به Grok Auth Broker و متغیرهای `GROK_AUTH_*` وابسته است.
- `src/lib/auth/email-password.ts` مقدار `false` دارد.
- `src/components/grill/app.tsx` نقش را از `settings.role` در Zustand می‌خواند و با select قابل تغییر است.
- فیلترکردن منو بر اساس نقش صرفاً رابط کاربری است و کنترل دسترسی سمت سرور ایجاد نمی‌کند.
- مسیر مدیریت حساب کاربران در UI/ API فعلی دیده نشد.

**راهکار:** ورود username/password در PHP، هش رمز با `password_hash`، session امن، CSRF، خروج امن، و RBAC در هر endpoint. ساخت اولین مدیر باید با فرایند نصب امن و بدون رمز ثابت انجام شود.

### 4. سفارش‌ها و اطلاعات عملیاتی فقط در مرورگر هستند
`src/lib/pos/store.ts` تمام داده‌های زیر را با Zustand persist در مرورگر ذخیره می‌کند: محصولات، دسته‌ها، مواد اولیه، مشتریان، کدهای تخفیف، سفارش‌ها، هزینه‌ها، الگوهای پیامک، لاگ پیامک، تنظیمات و شمارنده سفارش.

در نتیجه:
- دستگاه‌های مختلف دیتای مشترک ندارند.
- پاک‌شدن داده مرورگر یا تعویض دستگاه باعث از دست رفتن داده می‌شود.
- هم‌زمانی سفارش‌ها و شمارنده سفارش بین دستگاه‌ها ایمن نیست.
- منطق محاسبه مبلغ، امتیاز، تخفیف و کاهش موجودی فقط در کلاینت انجام می‌شود و باید به سرور منتقل شود.

**راهکار:** APIهای سمت سرور و تراکنش MySQL برای ثبت سفارش؛ محاسبه مجدد قیمت، تخفیف، امتیاز و موجودی در سرور. قفل/تراکنش و شماره سفارش اتمیک برای چند دستگاه.

### 5. پیامک از نظر محرمانگی نیازمند اصلاح است
`src/routes/api/sms.ts` اعتبارنامه پنل را از body مرورگر می‌گیرد. خود UI نیز `smsUser` و `smsKey` را از Zustand ارسال می‌کند. این اطلاعات باید از مرورگر خارج شوند و فقط در تنظیمات امن سرور نگهداری شوند.

ارسال پیامک به سرویس ملی‌پیامک وابسته است؛ این وابستگی ذاتی درگاه پیامک است، اما باید اختیاری باشد و قطع بودن سرویس پیامک نباید ثبت سفارش را مختل کند.

### 6. وابستگی‌های Grok و محیط پیش‌نمایش
در سورس مواردی از جمله موارد زیر وجود دارد:
- `src/components/preview-host-bridge.tsx`
- `src/lib/preview-host-bridge.ts`
- `src/lib/auth/gate-*`
- `src/lib/auth/popup.server.ts`
- `src/lib/app-data/*`
- `scripts/grok-pwa-*`
- `server/middleware/grok-pwa.ts`
- `server/virtual-grok-og-identity.d.ts`
- `.grok/*` و `public/__grok/*`

بخش‌هایی از این ساختار برای محصول نهایی لازم نیستند. باید بر اساس گراف import و مسیرهای واقعی build، با دقت حذف یا جایگزین شوند؛ حذف کورکورانه ممکن است به قابلیت نصب PWA یا رابط آسیب بزند.

### 7. وابستگی‌های خارجی رابط
- در `src/routes/__root.tsx` فونت Vazirmatn از Google Fonts دریافت می‌شود؛ برای استقلال ظاهری بهتر است فایل فونت داخل پروژه سرو شود.
- API پیامک به دامنه‌های `rest.payamak-panel.com` وابسته است؛ این اتصال فقط در زمان ارسال/استعلام پیامک لازم است.
- کتابخانه‌های npm برای Build رابط لازم‌اند، اما پس از Build، سرور PHP نباید برای اجرای برنامه به Node/npm نیاز داشته باشد.

## وضعیت UI/UX مشاهده‌شده

از اسکرین‌شات‌های موجود در آرشیو:
- ظاهر RTL و رنگ‌بندی فعلی یک هویت بصری مشخص دارد و قابل حفظ است.
- در دسکتاپ نوار ناوبری عمودی و کارت سفارش جاری قابل مشاهده‌اند.
- انتخاب نقش در Header باید با نام کاربر واردشده و خروج امن جایگزین شود.
- صفحه فروش در تصویر نمونه فضای خالی زیادی در ناحیه محصولات دارد؛ جست‌وجوی سریع محصول و چیدمان واکنش‌گرا می‌تواند کار صندوق را سریع‌تر کند.
- نسخه موبایل باید جداگانه بررسی و آزمون شود؛ اسکرین‌شات موجود به‌تنهایی برای تأیید UX موبایل کافی نیست.

در کد فعلی، ویرایش کامل سفارش توسط مدیر و مدیریت حساب کاربران به شکل یک جریان کامل مستقل تأیید نشد؛ این دو مورد باید در طراحی PHP و رابط نهایی پیاده‌سازی و تست شوند.

## معماری مقصد پیشنهادی

1. **Frontend:** React فعلی با حفظ UI، Build به فایل‌های استاتیک (HTML/CSS/JS)؛ هیچ runtime از Node روی هاست لازم نباشد.
2. **Backend:** PHP 8.x با API JSON، PDO، validation، مدیریت session، CSRF و کنترل نقش سمت سرور.
3. **Database:** MySQL/MariaDB با InnoDB، کلیدهای خارجی، indexها و تراکنش‌ها.
4. **Auth:** username/password؛ مدیر، صندوق‌دار، آشپز؛ حساب‌ها فقط توسط مدیر ساخته/غیرفعال شوند.
5. **POS:** تمام عملیات حساس در سرور؛ محاسبه مجدد سفارش در سرور؛ شماره سفارش و موجودی اتمیک.
6. **SMS:** اعتبارنامه در config خارج از web root یا environment؛ ارسال فقط برای مشتری؛ خطای پیامک از ثبت سفارش جدا باشد.
7. **Backup:** خروجی و بازیابی کنترل‌شده با اعتبارسنجی و دسترسی مدیر.

## ترتیب پیاده‌سازی و معیار پذیرش

### فاز 1 — پایه PHP/MySQL
- ساخت API bootstrap و config امن.
- ساخت schema و migration MySQL.
- ورود/خروج، session، CSRF، نقش‌ها و ایجاد امن مدیر اولیه.
- تست endpointها و آزمون دسترسی غیرمجاز.

### فاز 2 — انتقال عملیات POS
- API محصولات، دسته‌ها، مواد اولیه، مشتریان، تخفیف‌ها، سفارش‌ها، هزینه‌ها، تنظیمات و گزارش‌ها.
- انتقال منطق `quoteOrder` و محاسبه موجودی به PHP.
- تراکنش ثبت سفارش و آزمون هم‌زمانی چند دستگاه.
- عدم اتکا به localStorage برای داده مرجع.

### فاز 3 — اتصال رابط
- Build استاتیک React.
- شاشة ورود و مدیریت نشست.
- جایگزینی Zustand persist با API و cache فقط برای UX.
- نقش‌های واقعی و اصلاح مسیرهای مدیر/صندوق/آشپز.

### فاز 4 — پیامک، UI/UX و انتشار
- تنظیم امن درگاه پیامک و ثبت لاگ سمت سرور.
- میزبانی محلی فونت‌ها.
- آزمون RTL، موبایل، تبلت، دسکتاپ، چاپ رسید و PWA.
- آزمون نصب روی cPanel و مستند نصب/بکاپ/بازیابی.

## اطلاعات هاست که هنوز برای انتشار لازم است

کاربر تأیید کرده PHP و MySQL در هاست موجود است. هنوز نسخه دقیق PHP و فعال‌بودن PDO_MySQL، امکان ساخت دیتابیس/کاربر، SSL و Cron Job از طرف هاست در این بررسی مستند نشده‌اند. برای شروع توسعه می‌توان معماری PHP/MySQL را مبنا قرار داد؛ اما انتشار نهایی باید با این موارد آزموده شود.

# ممیزی محصول و سورس PersiaCoder POS — با نگاه بازار ایران

- تاریخ بررسی: 2026-11-19
- شاخه بررسی‌شده: `feature/3food-pos-next-release-v2`
- مبنای کد: commit `61a39ca7131eeb560c8a051b5621f236db4a4a0f`
- PR مرتبط: #4 — باز، Draft و Merge‌نشده
- روش: بررسی ایستای سورس، schema، API، رابط، تست‌ها، workflowها و اسناد؛ به‌همراه مرور صفحات عمومی چند راهکار بازار ایران.
- محدودیت: این ممیزی جایگزین اجرای کامل تست، تست staging روی cPanel/LiteSpeed، تست دستگاه واقعی، تست بانکی یا بررسی حقوقی/مالیاتی نیست. هیچ کد اجرایی در این ممیزی تغییر نکرده است.

## 1. نتیجه مدیریتی

**وضعیت فعلی: هسته اولیه POS با چند پایه فنی خوب؛ هنوز محصول تجاری آماده عرضه عمومی نیست.**

شاخه فعلی از یک UI متکی به مرورگر به سمت React استاتیک + PHP API + MySQL/InnoDB حرکت کرده است. بخش‌هایی از احراز هویت، نقش‌ها، محاسبه سروری قیمت، تراکنش سفارش، کنترل تکرار درخواست، دفتر اثرات سفارش و اتصال آزمایشی عامل کارتخوان وجود دارد. این‌ها پایه‌های ارزشمندی‌اند.

اما دامنه فعلی نرم‌افزار در عمل عمدتاً یک POS غذا و نوشیدنی ساده است؛ نه هنوز یک راهکار کامل رستورانی و نه POS فروشگاهی عمومی. اسناد V3 دو خانواده «غذا و نوشیدنی» و «فروشگاهی» را تصویب کرده‌اند، ولی این تصمیم هنوز در رابط و مدل داده پیاده نشده است.

**پیشنهاد تجاری:** ابتدا یک نسخه محدود، قابل اتکا و قابل پشتیبانی برای کسب‌وکارهای کوچک غذا و نوشیدنی آماده شود. خانواده فروشگاهی پس از طراحی مدل کالا/بارکد/مرجوعی/صندوق و انبار مستقل وارد توسعه شود. فعلاً محصول را به‌عنوان POS کامل فروشگاهی یا نرم‌افزار حسابداری معرفی نکنیم.

## 2. نقاط قوت واقعی موجود

1. رابط React/TypeScript به‌صورت SPA استاتیک ساخته می‌شود و اجرای روزمره Backend به Node وابسته نیست؛ Backend از PHP و PDO/MySQL استفاده می‌کند.
2. احراز هویت سمت سرور، هش رمز، session، CSRF، محدودسازی تلاش ورود، کنترل نقش و ثبت audit وجود دارد.
3. مبلغ سفارش در Backend دوباره محاسبه می‌شود؛ قیمت و گزینه‌های محصول از داده سرور خوانده می‌شوند و درخواست دستکاری‌شده کلاینت مرجع نهایی نیست.
4. ثبت سفارش از تراکنش MySQL، قفل ردیف‌ها، idempotency و دفتر اثرات قابل بازگردانی برای مصرف مواد و امتیاز مشتری استفاده می‌کند.
5. آشپز به اطلاعات تماس مشتری و یادداشت خصوصی سفارش دسترسی ندارد.
6. اعتبارنامه پیامک از پاسخ API و UI حذف شده و در تنظیمات خصوصی سرور نگهداری می‌شود.
7. Backup/restore مدیرمحور است؛ بازیابی روی دیتابیس خالی و با تراکنش انجام می‌شود.
8. عامل محلی کارتخوان از HTTPS و توکن هش‌شده استفاده می‌کند و در نبود درایور معتبر، پرداخت را موفق فرض نمی‌کند.
9. ساخت ویندوزی Terminal Agent در CI موفق بوده است؛ این موفقیت فقط build عامل را اثبات می‌کند، نه اتصال به کارتخوان بانکی واقعی.

## 3. موانع مسدودکننده عرضه (P0)

### P0-01 — CI شاخه فعلی شکست می‌خورد
- workflow run شماره 818 روی commit بررسی‌شده شکست خورده است.
- PHP syntax، نصب schema تازه MySQL و تست invariantهای تراکنشی موفق‌اند.
- تست یکپارچگی API در مرحله `cashier can read final terminal payment state` شکست می‌خورد.
- علت فنی: Frontend در `src/lib/api/php-client.ts` متد `getTerminalPayment(id)` را به مسیر `GET /terminal-payments/{id}` می‌فرستد و UI برای polling به آن وابسته است؛ اما endpoint متناظر در `php-backend/public/api/index.php` وجود ندارد. مسیر pending، cancel و attach-order وجود دارند، ولی مسیر دریافت جزئیات یک پرداخت مشخص وجود ندارد.
- به علت توقف workflow در این مرحله، TypeScript، unit tests، lint، build cPanel و smoke test بسته روی همین commit اجرا نشده‌اند.
- اولویت: رفع endpoint و افزودن تست مجوز manager/cashier/مالک پرداخت؛ سپس اجرای کامل workflow تا انتها.

### P0-02 — ویرایش سفارش می‌تواند روش پرداخت کارتی را بدون تأیید واقعی ثبت کند
- مسیر `PATCH /orders/{id}` فقط سفارش جدید را ویرایش می‌کند و روش پرداخت را از ورودی می‌پذیرد.
- در مسیر ویرایش، اعتبارسنجی وجود تراکنش کارتخوان approved با مبلغ یکسان و اتصال آن به سفارش مانند مسیر ایجاد سفارش انجام نمی‌شود.
- در نتیجه مدیر می‌تواند روش پرداخت سفارش را به card تغییر دهد بدون اینکه پرداخت بانکی متناظر وجود داشته باشد.
- اصلاح: یا تغییر روش پرداخت پس از ثبت را ممنوع کنیم، یا آن را از طریق جریان مستقل ثبت پرداخت/تراکنش تأییدشده انجام دهیم. هیچ مسیر UI نباید بتواند وضعیت پرداخت موفق را دستی جعل کند.

### P0-03 — وضعیت پرداخت از وضعیت سفارش جدا نیست
- `pos_orders` وضعیت سفارش و `payment_method` را نگه می‌دارد، اما چرخه مستقل payment_status، تسویه، بازپرداخت و تطبیق بانکی برای سفارش ندارد.
- وضعیت‌های سفارش مانند new/preparing/ready/delivered/cancelled نباید معادل پرداخت‌شده/پرداخت‌نشده/بازپرداخت‌شده تلقی شوند.
- لغو سفارش، اثر موجودی/امتیاز/تخفیف را برمی‌گرداند، اما مسیر refund بانکی/آنلاین و تطبیق نتیجه آن وجود ندارد.
- اصلاح: مدل مستقل سفارش، پرداخت، تسویه و بازپرداخت با شناسه مرجع بانکی، وضعیت قطعی/نامشخص و گزارش مغایرت.

### P0-04 — تنظیمات محاسبه سفارش برای صندوقدار کامل بارگذاری نمی‌شود
- در `/bootstrap`، تنظیمات کسب‌وکار فقط برای manager در منابع برگشتی قرار می‌گیرند؛ cashier تنظیمات سرور را دریافت نمی‌کند.
- UI در `hydratePosFromServer` برای تنظیمات غایب به seed مرورگر برمی‌گردد؛ مقدار پیش‌فرض taxPercent برابر صفر است.
- Backend مالیات، نرخ وفاداری و تبدیل امتیاز را از تنظیمات MySQL محاسبه می‌کند.
- اگر مدیر نرخ مالیات یا قواعد وفاداری را تغییر داده باشد، صندوقدار می‌تواند مبلغ متفاوتی محاسبه کند و سفارش با خطای mismatch رد شود.
- اصلاح: یک DTO امن و محدود از تنظیمات مؤثر فروش برای cashier برگردد؛ کلیدهای پیامک و تنظیمات حساس هرگز در آن نباشند. تست با مالیات و امتیاز سفارشی اضافه شود.

## 4. شکاف‌های محصول در برابر بازار ایران (P1)

### P1-01 — خانواده فروشگاهی هنوز پیاده نشده است
مدل فعلی Product شامل نام، دسته، قیمت، بهای ثبت‌شده، گزینه‌ها، رسپی و active است؛ فیلدهای پایه فروشگاه مانند barcode، SKU، تنوع/سایز/رنگ، وزن‌فروشی، واحد فروش و موجودی خود کالا در مدل دیده نمی‌شوند. جست‌وجوی صندوق نیز بر اساس نام محصول است.

نتیجه: فعلاً نباید محصول را POS فروشگاهی کامل معرفی کنیم. برای فروشگاهی حداقل بارکد، SKU، تنوع، موجودی کالای قابل فروش، مرجوعی، قیمت‌های چندسطحی، واحد/وزن، رسید خرید و گردش انبار لازم است.

### P1-02 — عملیات غذا و نوشیدنی هنوز حداقلی است
در مدل سفارش فعلی، کانال سفارش، میز/سالن، شماره میز، آدرس ارسال، پیک، بیعانه و ایستگاه آماده‌سازی به‌عنوان داده‌های مستقل دیده نمی‌شوند. UI فعلی صندوق منومحور است و مدیریت میز، نقشه سالن، تقسیم فاکتور، سفارش‌گیری گارسون، KDS واقعی و مسیریابی چاپ آشپزخانه در آن اثبات نشده است.

برای شروع بازار، زیرپروفایل رستوران/فست‌فود/کافه باید فقط پیش‌فرض‌ها و گردش‌کارهای مشترک را تنظیم کند؛ اما قابلیت‌های میز، بیرون‌بر، پیک، کمبو، سایز/دمای نوشیدنی و ایستگاه آشپزخانه باید مستقل و قابل تنظیم باشند.

### P1-03 — چاپ واقعی صندوق و آشپزخانه
مسیر چاپ مشاهده‌شده عمدتاً پیش‌نمایش رسید و `window.print()` مرورگر است. اتصال مستقیم ESC/POS، چاپ بی‌صدا، صف چاپ مقاوم، چند چاپگر و مسیریابی جداگانه غذا/نوشیدنی به‌صورت عملی تأیید نشده است.

برای رستوران ایرانی چاپ فیش آشپزخانه/بار و کار با چاپگر حرارتی یک قابلیت لوکس نیست؛ باید قبل از عرضه صنفی در staging با چند مدل رایج تست شود.

### P1-04 — شیفت و بستن صندوق وجود ندارد
در schema فعلی جدول یا مدل عملیاتی شیفت صندوق، وجه اول دوره، واریز/برداشت صندوق، شمارش پایان شیفت، مغایرت صندوق و تسویه به تفکیک صندوقدار دیده نمی‌شود.

این مورد برای فروش روزمره و کنترل صاحب کسب‌وکار اهمیت بالایی دارد. پیشنهاد می‌شود پیش از چندشعبه‌ای یا حسابداری پیشرفته، «شیفت و بستن صندوق» ساخته شود.

### P1-05 — انبار هنوز دفتر گردش کامل نیست
- مقدار موجودی مواد اولیه در JSON رکورد ingredient نگهداری می‌شود.
- `pos_order_effects` اثر مصرف مواد ناشی از سفارش را ثبت می‌کند، اما دفتر کل مستقل و عمومی همه ورود/خروج‌ها نیست.
- تعدیل دستی موجودی در audit log ثبت می‌شود، ولی سند گردش مستقل با نوع عملیات، علت، مرجع و مانده قبل/بعد ندارد.
- خرید تأمین‌کننده می‌تواند موجودی ماده اولیه و میانگین بهای آن را تغییر دهد، اما چرخه کامل رسید، برگشت خرید، انتقال، انبارگردانی و ضایعات اثبات نشده است.
- واحد ماده اولیه متن آزاد است و تبدیل واحد پایه/فرعی وجود ندارد.
- چند انبار، بچ/سری ساخت و تاریخ انقضا در schema فعلی دیده نمی‌شوند.

**سیاست موجودی فعلی دوگانه است:** تعدیل دستی موجودی منفی را رد می‌کند، اما ثبت سفارش غذا عمداً اجازه می‌دهد موجودی مواد اولیه منفی شود و تست هم این رفتار را انتظار دارد. این تصمیم می‌تواند برای فروش غذا به‌عنوان ثبت کسری/نیاز به تأمین قابل قبول باشد، اما نباید به کالای فروشگاهی تعمیم داده شود. سیاست باید بر اساس پروفایل و نوع موجودی قابل تنظیم باشد و کسری واقعی را در دفتر گردش ثبت کند.

### P1-06 — گزارش‌ها حسابداری رسمی نیستند
گزارش فعلی فروش، بهای تمام‌شده، هزینه و سود را از سفارش‌ها و رکوردهای JSON محاسبه می‌کند. دفتر کل دوطرفه، حساب‌های دریافتنی/پرداختنی کامل، خزانه، بانک، چک، تسویه صندوق، برگشت فروش، بازپرداخت، بستن دوره و کنترل اسناد حسابداری دیده نمی‌شود.

بنابراین عنوان و تبلیغ «حسابداری کامل» یا «سود قطعی» مناسب نیست. گزارش فعلی باید گزارش مدیریتی/عملیاتی تلقی شود تا زمانی که موتور مالی و تطبیق اعداد پیاده‌سازی و تست شوند.

### P1-07 — فروش نقدی مهمان نباید به اجبار شماره موبایل بخواهد
در UI فعلی، اگر مشتری از قبل انتخاب نشده باشد، ثبت سفارش به واردکردن موبایل معتبر 09 نیاز دارد و مشتری جدید ساخته می‌شود. برای فروش حضوری سریع، این الزام می‌تواند صف و اصطکاک ایجاد کند و جمع‌آوری داده غیرضروری را افزایش دهد.

پیشنهاد: فروش مهمان بدون موبایل مجاز باشد؛ موبایل فقط برای باشگاه، پیامک، سفارش ارسال یا صدور/ارسال فاکتور موردنیاز دریافت شود. رضایت پیامک باید مستقل و صریح باقی بماند.

### P1-08 — اتصال آنلاین به معنی درگاه پرداخت نیست
UI روش «آنلاین» را در کنار نقد و کارتخوان نمایش می‌دهد، اما درگاه پرداخت واقعی و تأیید server-to-server در سورس فعلی مشاهده نشد. تا زمان اتصال واقعی درگاه و آزمون callback، این گزینه باید حذف یا با عنوان «ثبت پرداخت خارجی/دستی» و قواعد روشن جایگزین شود.

### P1-09 — همگام‌سازی برای عملیات شلوغ کافی نیست
UI هر ۱۵ ثانیه bootstrap کامل را دریافت می‌کند و سفارش‌ها بدون صفحه‌بندی از دیتابیس خوانده می‌شوند. این روش برای شروع و حجم کم قابل استفاده است، اما برای چند صندوق و آشپزخانه در ساعت شلوغ، هم تأخیر ایجاد می‌کند و هم با رشد تاریخچه، payload و بار دیتابیس زیاد می‌شود.

پیشنهاد عملی روی هاست اشتراکی: endpointهای delta/paginated، دریافت سفارش‌های فعال با بازه محدود، polling کوتاه‌تر فقط برای صف فعال و backoff هنگام قطعی. WebSocket را تا وقتی زیرساخت مشتری واقعاً پشتیبانی نمی‌کند، پیش‌فرض نکنیم.

### P1-10 — آفلاین واقعی وجود ندارد
با حذف persist مرورگر، داده عملیاتی فقط از API دریافت می‌شود. هنگام قطع اینترنت/هاست، ثبت فروش جدید در رابط فعلی قابل اتکا نیست. آفلاین کامل پرهزینه است؛ اما باید از ابتدا تصمیم بگیریم کدام عملیات ضروری در قطع اینترنت مجاز است و چه داده‌ای با چه سیاست تعارضی همگام می‌شود. تا آن زمان نباید قابلیت «آفلاین» تبلیغ شود.

## 5. شکاف‌های مهم تکمیلی (P2)

1. **مدیریت قابلیت‌ها:** Feature Flag مرکزی، پلن، انتخاب مشتری و کاتالوگ قابلیت هنوز فقط در سند طراحی شده‌اند؛ UI و کنترل Backend آن پیاده نشده است.
2. **پروفایل‌های دوگانه:** تصمیم غذا و نوشیدنی/فروشگاهی در سند ثبت شده، اما NAV، مدل داده و onboarding کد هنوز عملاً غذا/منو محور است.
3. **پیامک:** رویدادهای مدل فعلی محدود به ثبت سفارش، آماده‌شدن، تحویل، امتیاز و تخفیف‌اند. کمپین و درخواست تولد در مرورگر به‌صورت ترتیبی ارسال می‌شوند؛ صف پایدار، retry کنترل‌شده، idempotency، محدودیت نرخ، ساعات سکوت و تطبیق کامل لاگ‌ها نیازمند تکمیل‌اند. UI فعلی فقط ملی‌پیامک را به‌عنوان provider مستند می‌کند.
4. **چندشعبه‌ای:** branch_id و مدل شعبه/انبار/صندوق در schema فعلی دیده نمی‌شود. این قابلیت نباید قبل از تثبیت هسته تک‌شعبه‌ای شروع شود.
5. **لایسنس و پنل مرکزی:** سرویس مرکزی لایسنس، پلن، فعال‌سازی ماژول‌ها و کنترل آفلاین هنوز در کد پیاده نشده است.
6. **مهاجرت داده:** سند پیاده‌سازی اعلام می‌کند import legacy فعلی سفارش‌های قدیمی را وارد نمی‌کند؛ برای ارتقای مشتریان V2 باید برنامه مهاجرت و تطبیق سفارش‌ها جداگانه طراحی شود.
7. **بکاپ:** export/restore دستی وجود دارد؛ بکاپ زمان‌بندی‌شده، نسخه خارج از هاست، رمزنگاری، هشدار شکست و تمرین دوره‌ای restore هنوز اثبات نشده است.
8. **برند:** سورس رابط هنوز عناوین 3Food POS/گریل‌کش را نمایش می‌دهد؛ برند ثابت PersiaCoder.ir و عبارت Powered by PersiaCoder.ir که در سند محصول تصویب شده‌اند، هنوز در UI اعمال نشده‌اند.
9. **سازگاری محیط:** preflight حداقل PHP 8.1 را قبول می‌کند، درحالی‌که محیط هدف پروژه PHP 8.2 اعلام شده است. ماتریس نسخه‌های واقعی MySQL/MariaDB و LiteSpeed/cPanel باید صریح و روی staging آزموده شود.
10. **امنیت CI:** workflow تست سطح دسترسی `contents: write` دارد، درحالی‌که job تست فقط به خواندن مخزن نیاز دارد. بهتر است job تست `contents: read` داشته باشد و هر عملیات commit/push lockfile در job جدا و محدود انجام شود.

## 6. مقایسه با انتظارات بازار ایران

مرور صفحات عمومی راهکارهای ایرانی و عرضه‌شده در بازار نشان می‌دهد مواردی مثل آفلاین/ادامه کار هنگام قطعی، چند کاربر و چند صندوق، چاپگرهای حرارتی و چاپ تفکیکی آشپزخانه، میز و سالن، KDS، بارکد، تنوع کالا، مرجوعی، واحدهای کالا و گردش انبار از موارد پرتکرار در معرفی رقبا هستند.

این شواهد از صفحات معرفی فروشندگان به دست آمده‌اند؛ ادعای فروشنده معادل تست مستقل نیست و برای تصمیم خرید/رقابت باید دمو و تست واقعی انجام شود.

## 7. پیشنهاد محدوده عرضه مرحله اول

### مرحله اول: غذا و نوشیدنی کوچک و تک‌شعبه
- صندوق سریع و ثبت سفارش مهمان بدون اجبار موبایل.
- محصولات/منو، افزودنی و قیمت‌گذاری سروری.
- نقد و کارتخوان فقط با درایور واقعی تأییدشده؛ درگاه آنلاین فقط پس از اتصال واقعی.
- وضعیت سفارش و صف آماده‌سازی.
- چاپ حرارتی واقعی مشتری و آشپزخانه با حداقل یک یا دو مدل تأییدشده.
- شیفت، بستن صندوق و گزارش فروش/تسویه روزانه.
- مواد اولیه، رسپی پایه، رسید خرید و دفتر گردش قابل ردیابی.
- مشتری و پیامک اختیاری با رضایت.
- نقش‌های manager/cashier/kitchen و بکاپ قابل بازیابی.
- نصب و ارتقا روی cPanel/LiteSpeed هدف با تست staging.

### مرحله دوم: تکمیل خانواده غذا و نوشیدنی
- میز و سالن، بیرون‌بر/پیک، چند ایستگاه چاپ، KDS، تقسیم فاکتور و گردش سفارش کامل.
- ضایعات، واحد و تبدیل، انبارگردانی و چند انبار در صورت تقاضای مشتریان پایلوت.
- کمپین پیامکی صف‌محور و گزارش سود با توضیح مبانی محاسبه.

### مرحله سوم: خانواده فروشگاهی
- بارکد/SKU، تنوع کالا، واحد/وزن، فروش سریع، مرجوعی/تعویض و موجودی کالای قابل فروش.
- خرید و رسید کالا، گردش انبار، قیمت‌های چندسطحی و شیفت صندوق.
- اتصال تجهیزات فروشگاهی و گزارش سود با بهای تمام‌شده معتبر.
- تست با فروشگاه واقعی (مثلاً سوپرمارکت و پوشاک) پیش از تبلیغ عمومی.

### مرحله چهارم: قابلیت‌های تجاری و تخصصی
- WooCommerce، چندشعبه‌ای، لایسنس مرکزی، پلن‌ها، ماژول‌های قابل روشن/خاموش و آفلاین پیشرفته.
- داروخانه فقط به‌عنوان محصول/پروفایل تخصصی پس از بررسی الزامات قانونی و یکپارچگی‌های موردنیاز؛ نه صرفاً یک قالب فروشگاه.

## 8. کارهایی که فعلاً توصیه نمی‌کنم

- ادعای POS فروشگاهی کامل پیش از بارکد، تنوع، مرجوعی و انبار کالای فروشگاهی.
- ادعای حسابداری رسمی یا انطباق کامل مالیاتی پیش از بررسی حقوقی و تست سامانه‌های مربوط.
- توسعه چندشعبه‌ای، آفلاین کامل و پنل مرکزی قبل از تثبیت عملیات تک‌شعبه‌ای.
- افزودن تعداد زیادی ماژول بازاری بدون مصاحبه و پایلوت.
- پیاده‌سازی درایور کارتخوان با حدس یا پروتکل تأییدنشده.
- بازنویسی یک‌باره دو فایل بزرگ؛ تفکیک تدریجی و همراه تست امن‌تر است.

## 9. ترتیب اقدام فنی پیشنهادی

1. رفع P0-01 تا P0-04 و سبزکردن کامل CI.
2. تست end-to-end فروش، ویرایش، لغو، پرداخت، refund و مغایرت؛ با دو صندوق مستقل.
3. تثبیت مدل سفارش/پرداخت/شیفت/موجودی و ایجاد دفتر گردش انبار.
4. تست چاپگر و کارتخوان واقعی؛ بدون ادعای پشتیبانی مدل‌های تست‌نشده.
5. تکمیل تجربه غذا و نوشیدنی و اجرای پایلوت با کسب‌وکار واقعی.
6. سپس طراحی و اجرای مستقل پروفایل فروشگاهی.
7. پس از اثبات نیاز و پایداری، ماژول‌ها، لایسنس، WooCommerce و چندشعبه‌ای.

## 10. معیار ورود به انتشار

- CI کامل روی همان commit سبز باشد؛ TypeScript، unit، lint، build و smoke اجرا شده باشند.
- نصب تازه و ارتقا از نسخه قبلی روی staging واقعی cPanel/LiteSpeed موفق باشد.
- سناریوهای ثبت هم‌زمان، قطع شبکه، تکرار درخواست، لغو، refund، موجودی و restore بدون مغایرت باشند.
- حداقل یک پایلوت واقعی برای هر پروفایل عرضه‌شده انجام شود.
- چاپگر و کارتخوان فقط برای مدل‌هایی اعلام شوند که تست عملی موفق دارند.
- نسخه پشتیبان خارج از هاست تهیه و بازیابی آن تمرین شده باشد.
- ادعاهای مالیاتی، حسابداری و امنیتی فقط بر اساس شواهد معتبر مطرح شوند.

## 11. وضعیت تغییرات این ممیزی

- فقط سورس، schema، workflow، تست‌ها و اسناد بررسی شدند.
- هیچ فایل اجرایی، schema عملیاتی یا دیتابیس production تغییر نکرد.
- این سند گزارش بررسی و پیشنهاد backlog است؛ هیچ موردی با ثبت در این سند به معنی پیاده‌سازی یا تکمیل‌شدن نیست.

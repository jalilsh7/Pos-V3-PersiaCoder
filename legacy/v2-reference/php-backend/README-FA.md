# 3Food POS — PHP/MySQL backend migration (مرحله توسعه)

این بسته شامل backend مبتنی بر PHP و MySQL و خروجی استاتیک React برای cPanel است. منطق اصلی سفارش، کنترل نقش‌ها، موجودی و وفاداری، بکاپ/بازیابی و ساخت بسته استقرار پیاده‌سازی شده و در CI با MySQL موقت و درخواست HTTP آزمایش می‌شود. **استقرار واقعی روی cPanel و آزمون پذیرش در محیط فروشگاه هنوز انجام نشده است**؛ تا پایان آن، این نسخه را staging در نظر بگیرید.

### نکات امنیتی پیش از انتشار

- API روی همه پاسخ‌ها هدرهای ضد MIME sniffing و framing، سیاست ارجاع محدود و CSP محدودکننده می‌فرستد؛ روی اتصال HTTPS نیز HSTS فعال است.
- درخواست‌های تغییردهنده باید از مبدأ هم‌طرح (scheme)، هم‌میزبان و هم‌درگاه باشند؛ درخواست‌های دارای Fetch Metadata از نوع cross-site رد می‌شوند. توکن CSRF همچنان الزامی است.
- انتشار فقط روی HTTPS انجام شود. پس از ساخت اولین مدیر، مقدار `setup_token` را از `private/config.php` حذف کنید و فایل تنظیمات را خارج از document root نگه دارید.
- به‌روزرسانی‌های هفتگی وابستگی‌های npm و GitHub Actions با Dependabot پیشنهاد می‌شوند؛ پیش از ادغام هر به‌روزرسانی، CI را بررسی کنید.

### پشتیبان‌گیری و بازیابی کامل

- مدیر می‌تواند از مسیر تنظیمات، پشتیبان JSON کامل MySQL را دریافت کند؛ شامل رکوردها، سفارش‌ها، وضعیت‌ها، دفتر اثرهای موجودی/وفاداری، دفتر مصرف کد تخفیف و شمارنده سفارش است. اعتبارنامه‌های پیامک عمداً صادر نمی‌شوند.
- بازیابی فقط برای مدیر و فقط روی دیتابیس مقصدی که جداول عملیاتی POS آن خالی باشند مجاز است. حساب‌های ورود، کاربران، نشست‌ها و گزارش‌های ممیزی مقصد حفظ می‌شوند؛ سفارش‌ها و دفترهای تراکنشی در یک تراکنش واحد بازسازی می‌شوند.
- روی دیتابیس پر، عملیات با پاسخ 409 رد می‌شود و هیچ داده‌ای بازنویسی نمی‌شود. ابتدا از مقصد پشتیبان بگیرید و برای بازیابی، دیتابیس POS خالی و سازگار آماده کنید.
- سقف فایل بازیابی ۸ مگابایت است. پس از بازیابی موفق، صفحه دوباره بارگذاری می‌شود.

## بسته استقرار cPanel

فرمان `npm run build:cpanel` در ریشه مخزن، پس از build استاتیک، پوشه `dist-cpanel/` را می‌سازد. ساختار آن برای حفظ مسیر امن config به این شکل است:
- `public/`: Document Root زیردامنه؛ شامل فایل‌های React، `.htaccess` و `api/index.php`
- `private/`: بیرون Document Root و هم‌سطح public؛ شامل `config.example.php` و deny rule
- `database/`: schema و migrationهای MySQL

در cPanel، Document Root را روی `dist-cpanel/public` قرار دهید و `dist-cpanel/private/config.example.php` را در پوشه private به `config.php` تبدیل کنید. جزئیات در `DEPLOYMENT-FA.md` داخل بسته آمده است. هیچ فایل config واقعی در build یا Git قرار نمی‌گیرد.

## نیازمندی‌ها
- PHP 8.2+ (حداقل کد PHP 8.1)
- افزونه‌های `PDO` و `pdo_mysql`
- MySQL 5.7.8+ یا MariaDB سازگار با JSON و InnoDB
- Apache با `mod_rewrite` و پشتیبانی `.htaccess`
- SSL فعال

## ساختار و نصب آزمایشی
1. در cPanel دیتابیس MySQL و کاربر اختصاصی بسازید و دسترسی کامل را فقط به همان دیتابیس بدهید.
2. `schema.sql` را در phpMyAdmin وارد کنید. اگر دیتابیس را قبلاً با نسخه قدیمی‌تر ساخته‌اید، فایل‌های `migrations/002-session-version.sql`، `migrations/003-order-idempotency.sql`، `migrations/004-order-effects-ledger.sql`، `migrations/005-order-discount-code.sql`، `migrations/006-discount-redemptions-ledger.sql` و در پایان `migrations/007-order-payment-and-guest-details.sql`، `migrations/008-global-appearance-settings.sql` و `migrations/009-payment-terminal-foundation.sql` را به‌ترتیب و هرکدام فقط یک‌بار اجرا کنید.
3. `private/config.example.php` را به `private/config.php` کپی کنید و اطلاعات دیتابیس را وارد کنید.
4. برای `app_key` و `setup_token` دو مقدار تصادفی مستقل با حداقل 64 نویسه hex تولید کنید. از قرار دادن آن‌ها در پوشه عمومی یا JavaScript خودداری کنید.
5. برای پیامک، فقط در `private/config.php` مقدار `sms.provider` را `national_payamak` و مقادیر `username`، `password` و `sender` را تنظیم کنید. این اطلاعات را در تنظیمات مرورگر یا فایل‌های Git قرار ندهید.
6. در ساختار سورس، Document Root را روی `php-backend/public` قرار دهید؛ در بسته تولیدی cPanel، Document Root روی `dist-cpanel/public` است. در هر دو حالت پوشه `private` باید sibling و بیرون Document Root باشد.
7. SSL را فعال کنید.
8. ابتدا `GET /api/v1/health` و سپس `GET /api/v1/preflight` را بررسی کنید. preflight نسخه PHP، افزونه‌های لازم، اتصال دیتابیس، جدول‌های InnoDB و HTTPS را گزارش می‌کند؛ فقط وقتی `production_ready` برابر true است وارد مرحله پذیرش عملیاتی شوید.
9. در صفحه ورود POS، راه‌اندازی اولیه را انجام دهید و توکن یک‌بارمصرف را وارد کنید. رمز باید حداقل 12 نویسه باشد.
10. پس از ایجاد مدیر، مقدار `setup_token` را از `private/config.php` حذف کنید.

## مرجعیت داده و مهاجرت از localStorage
بازیابی پشتیبان از مسیر PHP و فقط برای مدیر انجام می‌شود؛ مقصد باید دیتابیس عملیاتی خالی باشد. restore با قفل‌گذاری و تراکنش انجام می‌شود و داده‌های حساب‌ها، نشست‌ها و audit مقصد را حفظ می‌کند. فایل JSON را نمی‌توان با تغییر state مرورگر جایگزین کرد.


وضعیت POS دیگر با Zustand persist در `localStorage` ذخیره نمی‌شود؛ مجموعه‌های عملیاتی در شروع خالی هستند و هر پاسخ bootstrap متناسب با نقش، snapshot کامل رابط را جایگزین می‌کند. مجموعه‌ای که سرور برای آن نقش ارسال نکند نیز پاک می‌شود تا داده مدیر در نشست صندوق‌دار/آشپز باقی نماند. داده قدیمی کلید `grillcash-v1` فقط هنگام انتخاب صریح «انتقال داده این دستگاه به MySQL» خوانده می‌شود؛ پس از انتقال موفق حذف می‌شود و اعتبارنامه‌های پیامک پیش از ارسال حذف می‌شوند. فایل پشتیبان JSON نیز همچنان می‌تواند از رابط بازیابی و سپس با همین ابزار منتقل شود. این مسیر انتقال فقط یک‌بار و فقط به دیتابیس خالی کار می‌کند؛ تاریخچه سفارش‌ها در import قدیمی منتقل نمی‌شود.

## نکات مهم و محدودیت‌های باقی‌مانده
- صفحه اصلی React اکنون ورود، راه‌اندازی اولیه مدیر، تغییر اجباری رمز و خروج را با نشست PHP انجام می‌دهد؛ انتخاب دستی نقش از رابط حذف شده است.
- مدیر از بخش «کاربران» می‌تواند حساب مدیر/صندوق‌دار/آشپز بسازد، نقش را تغییر دهد و حساب را فعال یا غیرفعال کند؛ API از غیرفعال‌سازی آخرین مدیر فعال جلوگیری می‌کند.
- پس از ورود، رابط برای همگام‌سازی چنددستگاهی هر ۱۵ ثانیه bootstrap را دوباره می‌خواند و هنگام بازگشت پنجره/تب به حالت فعال نیز فوراً تازه‌سازی می‌کند. درخواست‌های هم‌زمان جلوگیری می‌شوند؛ خطای گذرای شبکه داده سالم فعلی را پاک نمی‌کند.
- در صفحه تنظیمات، مدیر می‌تواند داده‌های اصلی دستگاه را یک‌بار به دیتابیس خالی منتقل کند؛ این انتقال شامل دسته‌ها، محصولات، مواد اولیه، مشتریان، تخفیف‌ها، هزینه‌ها، قالب‌ها و تنظیمات است، اما تاریخچه سفارش‌ها را منتقل نمی‌کند. پس از آن داده‌های موجود از bootstrap سرور بارگذاری می‌شوند؛ همگام‌سازی خودکار همه ویرایش‌های بعدی UI هنوز تکمیل نشده است.
- مالیات از تنظیمات مرکزی فروشگاه قابل فعال/غیرفعال‌کردن است؛ در حالت غیرفعال، مالیات سفارش صفر محاسبه می‌شود. در حالت فعال، درصد تنظیم‌شده (۰ تا ۱۰۰) روی مبلغ پس از تخفیف‌ها اعمال می‌شود. API مقدار مالیات و مبلغ نهایی را با تنظیمات MySQL دوباره محاسبه و اعتبارسنجی می‌کند و به مبلغ مالیات ارسالی مرورگر اعتماد نمی‌کند. اقلام سفارش در PHP از روی محصولات و گزینه‌های ثبت‌شده در MySQL بازسازی می‌شوند؛ نام محصول، برچسب گزینه و قیمت ذخیره‌شده از مرورگر پذیرفته نمی‌شود. رکورد محصولات تا پایان تراکنش قفل و تغییر هم‌زمان قیمت/دستور ساخت باعث رد سفارش و نیاز به محاسبه مجدد می‌شود. مقدار و شناسه گزینه‌ها نیز کنترل و گزینه تکراری رد می‌شود.

کد تخفیف در PHP با داده مرکزی MySQL اعتبارسنجی می‌شود: بازه تاریخ، حداقل مبلغ، درصد/مبلغ ثابت، سقف تخفیف درصدی، سقف مصرف کلی، سطح عضویت و محدودیت هر مشتری. ثبت مصرف کد و سفارش در یک تراکنش و با قفل رکورد تخفیف انجام می‌شود؛ شمارش سهمیه از جدول تغییرناپذیر `pos_discount_redemptions` انجام می‌شود تا ویرایش دستی شمارنده نتواند محدودیت را دور بزند. کد مصرف‌شده در سفارش ذخیره می‌شود و با لغو سفارش، سهمیه آن نیز در همان تراکنش آزاد می‌شود. موجودی امتیاز مشتری اکنون هنگام ثبت سفارش در تراکنش و با قفل رکورد بررسی و به‌روز می‌شود.
- برای ثبت سفارش از `idempotencyKey` یکتای UUID استفاده کنید و هنگام retry همان کلید را دوباره بفرستید؛ استفاده دوباره از همان کلید با payload متفاوت با خطای 409 رد می‌شود.
- هنگام ثبت سفارش، مصرف مواد اولیه از recipe ذخیره‌شده سمت سرور محاسبه می‌شود؛ ردیف‌های انبار با `SELECT ... FOR UPDATE` قفل و کسر موجودی در همان تراکنش سفارش انجام می‌شود. سفارش در صورت ناکافی بودن موجودی یا نبودن ماده اولیه رد می‌شود. تغییر موجودی مشتری (کسر امتیاز، افزودن امتیاز، افزایش مبلغ خرید و تعداد مراجعه) نیز با قفل رکورد مشتری و در همان تراکنش انجام می‌شود؛ retry با idempotency key اثرها را دوباره اعمال نمی‌کند. اثرهای هر سفارش در جدول `pos_order_effects` ثبت می‌شوند. با لغو سفارش، موجودی مواد و اثر امتیاز/مبلغ خرید/تعداد مراجعه در همان تراکنش بازگردانده و اثرها یک‌بار علامت‌گذاری می‌شوند؛ درخواست لغو تکراری نمی‌تواند بازگشت را دوباره اعمال کند. اگر امتیاز کسب‌شده سفارش قبلاً خرج شده باشد، لغو با خطای 409 متوقف می‌شود تا موجودی امتیاز منفی یا ناسازگار نشود. سفارش‌های قدیمی که پیش از نصب ledger ثبت شده‌اند اثر قابل‌بازگشتی ندارند. آزمون هم‌زمانی روی MySQL واقعی، گزارش‌ها، بکاپ/بازیابی و همگام‌سازی بلادرنگ هنوز کامل نیستند.
- ارسال پیامک از مسیر PHP انجام می‌شود و اعتبارنامه از `private/config.php` خوانده می‌شود؛ رابط مرورگر فقط شماره، متن و شناسه الگو را می‌فرستد. فعال‌سازی واقعی نیازمند تنظیم اعتبارنامه و آزمایش ارسال در هاست است. نتیجه ارسال یا خطای ارسال در رکورد `sms_logs` ذخیره و در bootstrap مدیر بارگذاری می‌شود؛ اگر ذخیره گزارش هم شکست بخورد، رابط آن را در جزئیات خطا نشان می‌دهد.
- build استاتیک مخصوص cPanel از مسیر runtime قدیمی جدا شده و بسته `dist-cpanel/` در CI با موفقیت ساخته، اعتبارسنجی و به‌عنوان artifact منتشر شده است؛ تست واقعی Apache/PHP/MySQL و browser end-to-end هنوز باقی است.
- تغییرات اخیر در CI با PHP lint، TypeScript، تست‌های مستقل و ESLint بررسی می‌شوند؛ build استاتیک و آزمون end-to-end روی هاست هنوز باقی است. اتصال واقعی MySQL و ارسال پیامک نیز تا تنظیم cPanel تأییدشدنی نیست.

## آزمون ساختار MySQL در CI

در هر اجرای GitHub Actions، یک سرویس موقت MySQL 8.4 بالا می‌آید، `schema.sql` روی دیتابیس خالی اجرا می‌شود و اسکریپت `scripts/check-mysql-schema.php` وجود جدول‌های حیاتی، InnoDB بودن آن‌ها، ستون‌های لازم، ایندکس‌های یکتای idempotency/ledger و رکورد اولیه نصب را بررسی می‌کند. این آزمون خطاهای ساختاری schema را پیش از انتشار آشکار می‌کند؛ جایگزین آزمون تراکنش‌های واقعی سفارش، رقابت هم‌زمان کاربران یا سازگاری نسخه MySQL هاست cPanel نیست.

## بررسی نحوی
```bash
php -l public/api/index.php
```

**هشدار:** این بسته برای ادامه توسعه و تست staging است؛ آن را جایگزین نسخه عملیاتی صندوق نکنید.


### آزمون محدودیت‌های تراکنشی MySQL

در همان CI، پس از نصب schema، اسکریپت `scripts/check-mysql-transaction-invariants.php` نیز اجرا می‌شود. این آزمون با fixture موقت و rollback نهایی بررسی می‌کند که کلید idempotency سفارش، اثر یکتای هر منبع در ledger و ثبت redemption برای هر سفارش با قیدهای یکتای MySQL محافظت شوند. این تست قیدهای دیتابیس را پوشش می‌دهد؛ در CI، دو نشست مستقل به‌طور هم‌زمان برای سفارشی با مصرف بیش از موجودی باقی‌مانده رقابت می‌کنند؛ انتظار می‌رود دقیقاً یک سفارش ثبت شود، درخواست دیگر با 409 رد شود و موجودی منفی نشود. این آزمون روی MySQL 8.4 و PHP چند worker اجرا می‌شود؛ آزمون بار و رقابت طولانی‌مدت روی هاست واقعی همچنان لازم است.

### آزمون یکپارچهٔ API با MySQL

در CI، پس از نصب schema روی MySQL موقت، API PHP با تنظیمات آزمایشیِ تولیدشده در همان runner اجرا می‌شود. اسکریپت `scripts/check-php-api-integration.php` از طریق HTTP واقعی این موارد را بررسی می‌کند: راه‌اندازی یک‌باره مدیر و نشست، رد CSRF نامعتبر، ذخیره رکوردها، محاسبه قیمت از محصول سمت سرور، جلوگیری از تغییر قیمت ارسالی مرورگر، retry با idempotency key و رد payload متفاوت، رد سفارش با موجودی ناکافی، کسر موجودی و ثبت اثر مشتری، لغو سفارش و بازگشت یک‌باره موجودی/اثر مشتری. همچنین ساخت کاربر صندوق‌دار توسط مدیر، محدودیت دسترسی صندوق‌دار به مدیریت کاربران/محصولات، مجوز خواندن و افزودن مشتری، منع حذف مشتری توسط صندوق‌دار و فعال‌شدن محدودکننده ورود پس از ۸ تلاش ناموفق. همه داده‌ها فقط در دیتابیس موقت CI هستند؛ این آزمون جایگزین تست روی نسخه PHP/MySQL هاست واقعی یا آزمون بار هم‌زمانی چند صندوق‌دار نیست. همچنین bootstrap صندوق‌دار را از داده‌های انبار/هزینه/تنظیمات جدا می‌کند، خروجی آشپز را به اطلاعات آماده‌سازی محدود می‌سازد و نبود فیلدهای هویتی مشتری/یادداشت خصوصی را بررسی می‌کند. نوشتن و خواندن تنظیمات دارای فیلدهای آزمایشی SMS نیز بررسی می‌شود تا این مقادیر نه در پاسخ API ظاهر شوند و نه در دیتابیس ذخیره شوند. در پایان، غیرفعال‌سازی حساب صندوق‌دار توسط مدیر نیز با نشست قبلی همان صندوق‌دار آزمایش می‌شود تا نشست صادرشده پیش از لغو دسترسی دیگر معتبر نباشد.


## زیرساخت کارتخوان شبکه‌ای (مرحله پایه)

- مهاجرت `009-payment-terminal-foundation.sql` ساختار چندکارتخوان، چندعامل محلی و دفتر تراکنش کارتخوان را اضافه می‌کند؛ برای دیتابیس تازه همین ساختار در `schema.sql` وجود دارد.
- هر عامل محلی با شناسه مستقل و hash توکن نگهداری می‌شود؛ توکن خام نباید در دیتابیس یا log ذخیره شود. هر کارتخوان به یک عامل محلی و کلید محلی یکتا متصل است.
- اطلاعات دستگاه شامل شرکت پرداخت، مدل، کد درایور، LAN/Wi-Fi، IP، پورت و وضعیت پیش‌فرض است. مقدار پیش‌فرض درایور `unconfigured` است و به معنی پشتیبانی عملی از دستگاه نیست.
- دفتر پرداخت وضعیت‌های `queued`, `processing`, `approved`, `declined`, `cancelled`, `unknown`, `expired` را ثبت می‌کند. پاسخ خام حساس کارتخوان نباید ذخیره شود؛ فقط داده پاسخ پالایش‌شده و شناسه پیگیری/مرجع مجاز است.
- **این مرحله فقط زیرساخت داده است، نه اتصال عملیاتی کارتخوان.** هنوز API صف عامل محلی، جفت‌سازی امن، رابط مدیریت دستگاه، برنامه عامل ویندوز و درایورهای تأییدشده PSP پیاده‌سازی نشده‌اند. تا دریافت مستندات شرکت پرداخت و تست با دستگاه واقعی، پرداخت با کارتخوان نباید فعال یا به‌عنوان پرداخت موفق ثبت شود.

### چرخه امن پرداخت کارتخوان

- ثبت سفارش با روش `card` فقط وقتی مجاز است که `terminalPaymentId` به یک تراکنش `approved`، متعلق به همان کاربر و دقیقاً هم‌مبلغ سفارش اشاره کند؛ قفل و اتصال تراکنش به سفارش در همان تراکنش MySQL انجام می‌شود.
- برای جلوگیری از برداشت تکراری، وجود تراکنش در حال پردازش، نامشخص یا تأییدشده اما متصل‌نشده، پرداخت جدید روی همان کارتخوان را مسدود می‌کند؛ POS پس از refresh تراکنش باز خود را بازیابی می‌کند.
- عامل محلی با header اختصاصی `X-Terminal-Agent-Token` احراز هویت می‌شود. توکن خام فقط هنگام ساخت نمایش داده می‌شود و در MySQL فقط SHA-256 آن نگهداری می‌شود.
- اگر عامل محلی بیش از ۹۰ ثانیه heartbeat نداشته باشد، دستگاه برای پرداخت در دسترس محسوب نمی‌شود.
- در بازیابی پشتیبان، تنظیمات کارتخوان و دفتر تراکنش حفظ می‌شوند اما عامل‌ها و کارتخوان‌ها عمداً غیرفعال می‌شوند و باید دوباره جفت‌سازی/فعال شوند؛ هیچ توکن عامل در backup صادر نمی‌شود.
- API و آزمون CI فعلاً صف و پاسخ مصنوعی عامل را بررسی می‌کنند. **برنامه عامل ویندوز و درایورهای واقعی PSP هنوز پیاده‌سازی نشده‌اند؛ بنابراین هیچ مدل کارتخوان واقعی هنوز پشتیبانی عملیاتی ندارد.**


## وضعیت ایمنی پرداخت (PAY-B1)
- تا زمان اتصال درگاه بانکی واقعی و تأیید server-to-server، ثبت سفارش جدید با روش `online` در API با خطای `online_payment_unavailable` رد می‌شود؛ UI آن را با برچسب «آنلاین (به‌زودی)» غیرفعال نشان می‌دهد.
- سفارش دارای پرداخت کارتخوان یا سفارش آنلاین قدیمی تا تعیین‌تکلیف مالی و ثبت بازپرداخت قابل ویرایش نیست.
- لغو سفارش کارت‌پرداخت‌شده یا سفارش آنلاین قدیمی بدون فرایند تطبیق/بازپرداخت مجاز نیست. لغو سفارش به‌تنهایی هیچ تراکنش بانکی را refund نمی‌کند.
- سوابق سفارش‌های آنلاین قدیمی حفظ می‌شوند؛ این سوابق به‌صورت خودکار پرداخت موفق تلقی نمی‌شوند.
- هنوز دفتر مستقل پرداخت، بازپرداخت نقدی، بازپرداخت بانکی، پرداخت ترکیبی و تطبیق تسویه پیاده‌سازی نشده‌اند. برای مدل و برنامه اجرا به `PAYMENT_LEDGER_V3.md` مراجعه کنید.
- این بسته در CI با MySQL موقت، تست API، TypeScript، unit، lint، build، browser smoke و performance audit بررسی شده است؛ این نتیجه جایگزین تست staging واقعی cPanel/LiteSpeed، کارتخوان بانکی یا درگاه واقعی نیست.

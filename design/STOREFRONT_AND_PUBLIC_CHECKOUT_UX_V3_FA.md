> تصمیم محصول، یک قالب آنلاین عمومی و منعطف برای کسب‌وکارهای منودار است؛ برای هر صنف فروشگاه مستقل ساخته نمی‌شود. سند حاضر UX هدف را تعریف می‌کند و storefront فعلی صرفاً preview محلی است؛ در HEAD بررسی‌شده public catalog/checkout API یا route عمومی ثبت سفارش مشاهده نشده است.

## 1. هدف و تصمیم‌های قطعی محصول

- یک قالب storefront برای رستوران، کافه، فست‌فود، آبمیوه‌فروشی، بستنی‌فروشی و کسب‌وکارهای مشابه.
- تفاوت صنف از طریق دسته‌بندی، گروه محصول، تصویر، تنوع، افزودنی، قیمت، توضیحات، ترتیب نمایش و تنظیمات ظاهری ایجاد می‌شود.
- کاتالوگ و موتور سفارش مشترک با POS استفاده شود؛ storefront نباید کاتالوگ، قیمت یا سفارش موازی بسازد.
- سفارش آنلاین در مرکز سفارش‌ها و عملیات آماده‌سازی دیده شود.
- فروشگاه باید تجربه ساده، سریع، فارسی/RTL، واکنش‌گرا و مینیمال داشته باشد.
- برند ثابت PersiaCoder.ir و عبارت Powered by PersiaCoder.ir حفظ شود؛ White-Label یا حذف برند در طراحی قرار نگیرد.

## 2. ممیزی وضعیت فعلی

### UI
`StorefrontWorkspace.tsx`:
- از آرایه `menuItems` ثابت و نمونه استفاده می‌کند.
- دسته، جست‌وجو، quantity و cart با state محلی مرورگر انجام می‌شود.
- روش دریافت فقط pickup/delivery نمایشی است.
- وضعیت باز بودن، نام کسب‌وکار، متن cover و availability نمونه هستند.
- صفحه صریحاً اعلام می‌کند ثبت سفارش، هزینه ارسال، پرداخت، موجودی و ساعات کاری به Backend متصل نیست.
- دکمه checkout غیرفعال است.

### Backend
- در routeهای جاری، public storefront/catalog/checkout API مشاهده نشد.
- OrderService کانال `storefront` را در enum سفارش می‌شناسد؛ اما route سفارش موجود پشت session middleware و permission قرار دارد و endpoint عمومی storefront نیست.
- OrderService قیمت محصول، تنوع، گزینه‌ها و مالیات را سمت سرور از Catalog می‌خواند؛ این منطق برای استفاده مجدد در public checkout باید از طریق application API امن فراخوانی شود، نه منطق قیمت‌گذاری جدید در Frontend.
- schema کانال storefront و fulfillment delivery را می‌شناسد؛ این موضوع به معنی public checkout، پرداخت آنلاین یا مدیریت محدوده ارسال نیست.
- ساعات کاری، وضعیت open/closed و delivery zones در public runtime بررسی‌شده endpoint/contract فعال ندارند.

## 3. ساختار صفحه فروشگاه

### سربرگ کسب‌وکار
- لوگو/تصویر برند از Media API.
- نام کسب‌وکار و توضیح کوتاه.
- وضعیت باز/بسته از تنظیمات سرور؛ زمان آخرین به‌روزرسانی و پیام ساعات کاری در صورت داده معتبر.
- اطلاعات تماس/نشانی فقط از Business Profile API آینده.

### بنر و معرفی
- تصویر یا بنر اختیاری.
- پیام معرفی قابل تنظیم.
- در حالت بدون تصویر، طرح ساده و بدون فضای خالی بزرگ.

### دسته‌بندی منو
- دسته‌های فعال و مرتب‌شده از Catalog API.
- پیمایش افقی دسته‌ها در موبایل و فهرست ساده در دسکتاپ.
- دسته بدون محصول فعال نمایش داده نشود یا رفتار آن طبق قرارداد API باشد.
- جست‌وجوی نام/توضیح/SKU فقط در داده عمومی مجاز و از API سرور تغذیه شود.

### کارت محصول
- تصویر.
- نام و توضیح کوتاه.
- قیمت پایه.
- وضعیت availability واقعی.
- نشان «از ...» فقط اگر قیمت نهایی وابسته به تنوع/افزودنی باشد و مقدار حداقل از Backend محاسبه شده باشد.
- اقدام افزودن به سبد.
- گزینه/تنوع لازم قبل از افزودن، اگر محصول variant-required باشد.

## 4. جزئیات محصول و افزودنی

- تنوع‌ها از Catalog API و فقط گزینه‌های فعال.
- گروه گزینه و optionهای فعال همراه min/max و required در scope محصول.
- قیمت اختلافی تنوع و افزودنی از Backend؛ کلاینت صرفاً preview می‌کند.
- محدودیت انتخاب‌ها هنگام افزودن به cart اعتبارسنجی و هنگام checkout دوباره در Backend بررسی شود.
- تغییر قیمت یا غیرفعال‌شدن گزینه بین زمان افزودن و checkout باید با refresh و نمایش اختلاف به مشتری مدیریت شود؛ قیمت cart در مرورگر مرجع نیست.
- محصول بدون تنوع نباید انتخاب variant اجباری داشته باشد.
- snapshot سفارش باید نام، قیمت، SKU، تنوع و گزینه انتخابی را حفظ کند؛ تغییر بعدی کاتالوگ سفارش قبلی را عوض نکند.

## 5. سبد خرید

هر ردیف:
- محصول و تصویر کوچک.
- تنوع انتخابی.
- گزینه‌ها/افزودنی‌ها.
- تعداد.
- قیمت واحد و مبلغ ردیف از محاسبه server.
- حذف یا تغییر تعداد.

قواعد:
- cart local برای تجربه موقت قابل استفاده است؛ پس از refresh باید بازیابی فقط از یک cart persistence امن و قراردادی انجام شود، نه فرض ذخیره محلی دائمی.
- افزودن دوباره یک محصول با گزینه‌های متفاوت باید ردیف جدا بسازد.
- quantity، گزینه‌ها و قیمت هنگام checkout در Backend مجدداً validate شوند.
- اگر محصول غیرفعال/ناموجود یا قیمت تغییر کرده باشد، checkout متوقف و سبد با پیام روشن اصلاح شود.
- سبد خالی، loading، خطای شبکه و عدم availability حالت مستقل دارند.

## 6. Checkout

فرم پیشنهادی مرحله‌ای:
1. روش دریافت.
2. مشخصات مشتری/گیرنده.
3. آدرس یا اطلاعات دریافت.
4. زمان دریافت (فقط در صورت تصمیم و API پشتیبانی‌شده).
5. مرور سفارش و مبالغ.
6. انتخاب روش پرداخت و تأیید.

### روش دریافت
schema فعلی fulfillment:
- dine_in
- takeaway
- delivery

در storefront، روش‌های قابل انتخاب باید از تنظیمات فعال کسب‌وکار و شعبه بیایند؛ UI نباید pickup/delivery را برای همه کسب‌وکارها hard-code کند.

### مشخصات مشتری
- نام و شماره تماس گیرنده.
- شماره به شکل canonical در Backend validate شود.
- مهمان/مشتری ثبت‌شده طبق policy مصوب؛ ساخت خودکار customer profile بدون رضایت/قاعده مشخص فرض نشود.
- اطلاعات آدرس به‌صورت snapshot سفارش ذخیره شود.
- اطلاعات مشتری و آدرس فقط در scope مجاز و برای fulfillment نمایش داده شود.

### آدرس و محدوده ارسال
- فیلدهای نشانی از تنظیمات/قرارداد delivery آینده.
- delivery zone و هزینه ارسال فقط از سرور محاسبه شوند.
- اگر آدرس خارج محدوده باشد، ثبت سفارش delivery متوقف و روش جایگزین فقط در صورت فعال‌بودن پیشنهاد شود.
- هزینه ارسال از مبلغ پایه محصول جدا و در خلاصه مبلغ نمایش داده شود.
- هیچ مبلغ ارسال یا محدوده جغرافیایی در Frontend حدس زده نشود.

### زمان دریافت
- پیش‌سفارش/زمان‌بندی فقط در صورت policy مصوب و API معتبر.
- timezone کسب‌وکار/شعبه مرجع است.
- ظرفیت، lead time، cutoff و تعطیلات هنوز نیازمند قرارداد است.

## 7. ساعات کاری و باز/بسته بودن فروشگاه

نیاز UX:
- وضعیت فروشگاه از Backend و timezone مؤثر شعبه.
- برنامه هفتگی و استثناهای تعطیلی.
- کنترل دستی باز/بسته‌کردن توسط مدیر مجاز.
- policy سفارش هنگام تعطیلی (عدم سفارش، پیش‌سفارش یا نمایش منو) فقط پس از تصمیم محصول.

وضعیت فعلی:
- BusinessSetup timezone کسب‌وکار/شعبه را نگهداری می‌کند.
- در مسیرهای بررسی‌شده جدول/سرویس/route کامل ساعات کاری و open/close فروشگاه مشاهده نشد.
- تا ایجاد API، نشان «باز» یا «بسته» نباید از ساعت دستگاه یا مقدار نمایشی ثابت ساخته شود.

## 8. محاسبه قیمت و پرداخت

- تمام قیمت‌ها، tax، discount، delivery fee و total از Backend محاسبه شوند.
- OrderService فعلی subtotal/tax/total را سمت سرور محاسبه می‌کند؛ اما تخفیف و هزینه ارسال در مسیر فعلی صفر هستند.
- payment schema وجود دارد، اما PaymentService/route checkout عمومی در runtime فعلی اثبات نشده است.
- پرداخت آنلاین فقط با provider واقعی، server-to-server verification، callback امن و payment ledger فعال شود.
- redirect برگشت مرورگر به‌تنهایی موفقیت پرداخت نیست.
- timeout یا نتیجه نامشخص باید وضعیت pending/unknown و استعلام امن داشته باشد.
- checkout نباید سفارش paid بسازد بدون payment capture معتبر.
- شکست SMS یا سرویس جانبی نباید ثبت سفارش/پرداخت موفق را rollback کند.

## 9. ثبت سفارش و یکپارچگی

جریان هدف:
1. دریافت public catalog/availability.
2. اعتبارسنجی cart و انتخاب‌ها در Backend.
3. محاسبه قیمت/مالیات/هزینه ارسال در Backend.
4. ایجاد سفارش با source_channel=storefront و snapshot کامل.
5. ایجاد payment attempt/transaction مستقل.
6. نمایش نتیجه ثبت سفارش و وضعیت پرداخت جداگانه.
7. ارسال event به مرکز سفارش/آماده‌سازی.
8. پیامک تراکنشی در outbox/queue، مستقل از transaction اصلی.
9. update status و customer history از موتور مشترک.

در حال حاضر مراحل 1، 2، 4 از مسیر public، 5، 7 و 8 به‌صورت end-to-end در runtime اثبات نشده‌اند؛ این فلو معماری هدف است.

## 10. حالت‌ها و خطاها

- فروشگاه باز/بسته/وضعیت نامشخص.
- محصول ناموجود/غیرفعال/قیمت تغییرکرده.
- cart empty.
- invalid option/variant.
- آدرس خارج محدوده.
- روش دریافت غیرفعال.
- slot زمانی پر یا نامعتبر، فقط اگر زمان‌بندی فعال شود.
- checkout validation error.
- payment pending/failed/unknown.
- duplicate submit/idempotency replay.
- network failure و refresh امن وضعیت.
- permission/entitlement disabled در مدیریت؛ public storefront فقط با مجوز فعال نمایش داده شود.
- حالت maintenance یا اتصال backend unavailable.
- RTL، mobile-first، دسترس‌پذیری، target لمسی و focus.

## 11. مدیریت storefront در پنل

تنظیمات پیشنهادی:
- فعال/غیرفعال‌کردن storefront با entitlement و setting.
- نام/شعار/لوگو/بنر.
- ترتیب دسته‌ها و محصولات.
- نمایش/عدم نمایش محصولات فعال.
- متن معرفی و اطلاعات تماس.
- روش‌های دریافت.
- ساعات کاری و تعطیلی.
- delivery zone و fee.
- سیاست checkout و پرداخت.

فقط بخش‌هایی که API و permission واقعی دارند فعال شوند؛ در وضعیت فعلی این‌ها عمدتاً نیازمندی طراحی‌اند و نباید با state محلی به‌عنوان تنظیمات پایدار ارائه شوند.

## 13. معیار پذیرش

- [ ] یک storefront عمومی برای همه صنف‌های هدف با داده/تنظیمات متفاوت کار می‌کند.
- [ ] کاتالوگ، قیمت، تنوع و افزودنی از Catalog مشترک خوانده می‌شوند.
- [ ] availability از سرور است؛ نمونه ثابت یا state محلی مرجع نیست.
- [ ] cart گزینه‌ها و snapshot انتخاب را حفظ می‌کند و checkout دوباره validate می‌شود.
- [ ] روش دریافت، ساعات کاری و delivery zone فقط از API معتبر خوانده می‌شوند.
- [ ] قیمت، tax، discount و fee سمت Backend محاسبه می‌شوند.
- [ ] سفارش آنلاین از همان OrderService/domain مشترک ایجاد می‌شود.
- [ ] وضعیت سفارش و پرداخت جدا نمایش داده می‌شوند.
- [ ] پرداخت آنلاین فقط پس از verification واقعی موفق اعلام می‌شود.
- [ ] خطای سرویس جانبی، فروش/پرداخت را rollback نمی‌کند.
- [ ] مرکز سفارش، انبار و پیامک از eventهای معتبر مشترک تغذیه می‌شوند.
- [ ] تجربه mobile-first، RTL، accessible و برند ثابت حفظ می‌شود.

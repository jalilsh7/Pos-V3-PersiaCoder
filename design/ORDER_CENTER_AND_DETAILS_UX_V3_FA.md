- بسته بک‌لاگ: D-07
- وابستگی: `design/UI_SHELL_DASHBOARD_V3_FA.md`، `design/POS_SALES_WORKSPACE_V3_FA.md` و `design/PAYMENT_AND_RECEIPT_UX_V3_FA.md`

> این سند مشخصات UX است، نه ادعای تکمیل مرکز سفارش. قرارداد Backend در HEAD بررسی‌شده شامل فهرست، جزئیات، تاریخچه تغییر وضعیت و انتقال وضعیت سفارش است. تاریخچه تراکنش‌های پرداخت، عملیات refund و timeline جامع همه رویدادهای مالی در پاسخ فعلی جزئیات سفارش اثبات نشده‌اند و در طراحی به‌عنوان داده موجود فرض نمی‌شوند.

## 1. هدف و نقش‌ها

مرکز سفارش، نقطه واحد مشاهده و پیگیری سفارش‌های کانال‌های مختلف در یک شعبه است. کاربر باید بدون ورود به چند صفحه بتواند سفارش را پیدا کند، وضعیت سفارش و پرداخت را جداگانه بفهمد و فقط اقداماتی را ببیند که Backend برای نقش و وضعیت فعلی مجاز می‌داند.

نقش‌های مخاطب:
- صندوق‌دار: مشاهده سفارش‌های شعبه و پیگیری سفارش‌های ثبت‌شده از POS؛ اقدام فقط با مجوز واقعی.
- مدیر شعبه/مدیر کسب‌وکار: نظارت و انجام عملیات دارای مجوز.
- آشپزخانه: مشاهده سفارش‌های مرتبط و تغییر وضعیت‌های مجاز آشپزخانه؛ مجوز `kitchen.update` در Backend بررسی می‌شود.
- پشتیبانی/اپراتور سفارش: مشاهده و پیگیری؛ دسترسی نوشتن فقط در صورت تعریف مجوز سمت سرور.

## 2. اصول تجربه

- مینیمال، شیک، سریع و کم‌ازدحام؛ جدول/فهرست خوانا و جزئیات لایه‌بندی‌شده.
- فهرست و جزئیات از API و داده Backend تغذیه شوند؛ seed یا local state منبع حقیقت نباشد.
- وضعیت سفارش و پرداخت دو شاخص مستقل‌اند.
- مبلغ، زمان، مشتری و شناسه سفارش از پاسخ سرور نمایش داده شوند.
- مرکز سفارش همه کانال‌ها را با یک مدل واحد نمایش می‌دهد؛ کانال فقط یک مشخصه سفارش است.
- هیچ transition، refund یا عملیات مالی از روی ظاهر UI اختراع نشود.
- هر تغییر وضعیت باید نتیجه قطعی سرور را منعکس کند؛ در timeout وضعیت نامشخص باقی می‌ماند تا استعلام/بارگذاری مجدد انجام شود.

## 3. ساختار صفحه فهرست

### سربرگ
- عنوان «مرکز سفارش‌ها».
- انتخاب شعبه فقط در چارچوب BusinessScope و شعبه‌های مجاز؛ تغییر شعبه باید داده فهرست را از نو بارگذاری کند.
- شمارنده فقط در صورت وجود مقدار معتبر از API؛ شمارش کل از صفحه‌بندی محدود استنتاج نشود.

### نوار فیلتر
فیلترهای پشتیبانی‌شده در قرارداد فعلی:
- وضعیت سفارش: `draft`, `awaiting_payment`, `accepted`, `preparing`, `ready`, `completed`, `cancelled`, `rejected`.
- کانال: `pos`, `phone`, `manual`, `table`, `takeaway`, `storefront`.
- وضعیت پرداخت: `unpaid`, `partial`, `paid`, `refunded`, `partially_refunded`, `failed`, `pending`.
- روش دریافت: `dine_in`, `takeaway`, `delivery`.
- بازه تاریخ محلی شعبه/کسب‌وکار با فرمت API برابر `YYYY-MM-DD`.

قواعد:
- فیلترهای پرکاربرد در ردیف اول و فیلترهای تکمیلی در بخش جمع‌شونده.
- «پاک‌کردن فیلترها» همه فیلترها را به حالت پیش‌فرض برگرداند.
- مقدار تاریخ با timezone مؤثر شعبه تفسیر می‌شود؛ UI نباید timezone دستگاه را جایگزین timezone کسب‌وکار کند.
- بازه بیش از 366 روز، تاریخ نامعتبر یا شروع بعد از پایان باید با پیام قابل‌فهم نمایش داده شود؛ Backend نیز آن را رد می‌کند.
- جست‌وجوی متنی نام مشتری/شماره سفارش هنوز در قرارداد فهرست بررسی‌شده دیده نشده است؛ تا اضافه‌شدن API، کنترل جست‌وجو نباید وانمود کند که روی همه رکوردها جست‌وجوی سروری انجام می‌دهد.

### فهرست سفارش‌ها
نمایش پیشنهادی هر ردیف:
1. شماره سفارش و زمان ثبت.
2. نام مشتری یا «مشتری مهمان».
3. کانال سفارش با برچسب متنی.
4. تعداد اقلام، در صورت وجود داده در endpoint فهرست؛ در قرارداد فعلی این فیلد ارائه نشده و نباید تخمین زده شود.
5. روش دریافت در صورت ثبت.
6. مبلغ کل و واحد پول از سرور.
7. وضعیت سفارش.
8. وضعیت پرداخت، جدا از وضعیت سفارش.

رفتار:
- مرتب‌سازی پیش‌فرض جدیدترین شماره سفارش به قدیمی‌ترین است.
- صفحه‌بندی cursor-based با `next_cursor` و `has_more`؛ cursor بر مبنای شماره سفارش است. دکمه «نمایش بیشتر» یا بارگذاری تدریجی، بدون offset ساختگی.
- limit درخواست در Backend بین 1 تا 100 است؛ مقدار UI پیش‌فرض محافظه‌کارانه و ثابت باشد.
- انتخاب ردیف، صفحه/پنل جزئیات را با شناسه عمومی سفارش باز کند.
- تغییر هر فیلتر، cursor قبلی را پاک و درخواست جدید ایجاد کند.

## 4. صفحه جزئیات سفارش

### سربرگ خلاصه
- شماره سفارش، شناسه کوتاه قابل کپی و زمان ثبت.
- کانال سفارش.
- دو وضعیت مستقل و برجسته: «وضعیت سفارش» و «وضعیت پرداخت».
- اقدام بازگشت به فهرست بدون از دست دادن فیلترهای قبلی.

### اطلاعات مشتری و دریافت
- مشتری متصل‌شده یا «مشتری مهمان».
- اطلاعات دریافت بر اساس fulfillment: روش، نام گیرنده، تلفن و نشانی snapshot؛ فقط داده‌ای که API برمی‌گرداند.
- سفارش میز: شناسه/ارجاع میز یا نشست فقط اگر داده معتبر در API وجود داشته باشد.
- اطلاعات تماس حساس فقط برای نقش مجاز و در حد نیاز عملیاتی نمایش داده شوند.

### اقلام
- نام snapshot کالا، تنوع، SKU در صورت وجود.
- تعداد، قیمت واحد، تخفیف، مالیات و مبلغ ردیف.
- گروه و گزینه‌های انتخاب‌شده با تعداد و اختلاف قیمت.
- نام و قیمت snapshot سفارش تاریخی حفظ شوند؛ تغییر بعدی کاتالوگ نباید جزئیات سفارش گذشته را بازنویسی کند.

### خلاصه مبالغ
- مبلغ پایه/زیرجمع، تخفیف، مالیات، هزینه دریافت/ارسال و مبلغ کل.
- همه مقادیر از Backend؛ فرمت پول بر اساس `currency_code` و قرارداد واحد داخلی.
- فیلدهای تخفیف و هزینه ارسال فقط در صورت وجود در پاسخ جزئیات نمایش داده شوند.
- این endpoint در قرارداد بررسی‌شده، تراکنش‌های پرداخت، مبلغ پرداخت‌شده، مانده و ردیف‌های refund را برنمی‌گرداند؛ این اطلاعات نباید با محاسبه فرانت‌اند یا استنتاج از `payment_status` ساخته شوند.

## 5. تاریخچه و timeline

بخش «تاریخچه وضعیت سفارش» از `status_history` فعلی ساخته شود:
- زمان رویداد.
- وضعیت قبلی و وضعیت جدید.
- کانال/منبع ثبت رویداد.
- actor در صورت وجود.
- کد و متن دلیل در صورت وجود.

مرتب‌سازی مطابق ترتیب زمانی پاسخ API حفظ شود. اگر تاریخچه خالی است، پیام «رویدادی برای نمایش ثبت نشده است» نمایش داده شود.

محدوده timeline:
- تاریخچه فعلی، رویدادهای تغییر وضعیت سفارش است؛ آن را timeline جامع پرداخت، چاپ، پیامک، انبار یا تحویل معرفی نکن.
- تاریخچه پرداخت/refund و رویدادهای بین‌ماژولی پس از ایجاد قرارداد API و eventهای واقعی به این صفحه افزوده شوند.
- برای جلوگیری از نمایش ترتیب جعلی، زمان یا actor مفقود را حدس نزن.

## 6. اقدامات و انتقال وضعیت

فقط عملیات مجاز زیر از طریق API واقعی و policy سرور ارائه شوند؛ UI صرفاً راهنمای دسترسی است و مرجع مجوز نیست.

### انتقال‌های تعریف‌شده در کد فعلی
- `draft` → `awaiting_payment`, `accepted`, `cancelled`, `rejected`
- `awaiting_payment` → `accepted`, `cancelled`, `rejected`
- `accepted` → `preparing`, `ready`, `completed`, `cancelled`
- `preparing` → `ready`, `cancelled`
- `ready` → `completed`, `cancelled`
- `completed`, `cancelled`, `rejected` → بدون انتقال بعدی در state machine فعلی.

محدودیت مجوز:
- لغو/رد: مجوز `orders.cancel`.
- انتقال به `preparing` یا `ready`: مجوز `kitchen.update`.
- مسیر محدود آشپزخانه فقط `preparing` و `ready` را می‌پذیرد.
- سایر انتقال‌ها نیز باید از کنترل مجوز/سیاست endpoint عبور کنند؛ نبود کنترل UI به معنی مجازبودن عملیات نیست.

### لغو و رد
- دلیل لغو/رد اجباری است؛ کد یا متن دلیل باید ارسال شود.
- اگر سفارش پرداخت‌شده باشد، Backend فعلی لغو/رد را با خطای `refund_required_before_cancellation` متوقف می‌کند.
- لغو سفارش، refund نیست. جریان refund باید مستقل، با مجوز و ledger/provider خودش طراحی و پیاده‌سازی شود.
- برای سفارش دارای پرداخت، UI نباید دکمه لغو را به‌عنوان راه برگشت وجه نمایش دهد؛ کاربر باید به جریان مستقل refund هدایت شود، فقط اگر آن جریان واقعاً در دسترس باشد.

### ارسال درخواست و نتیجه
- برای هر انتقال، idempotency key و دلیل در صورت نیاز ارسال شود.
- هنگام درخواست، کنترل اقدام قفل و progress نمایش داده شود.
- پس از پاسخ موفق، جزئیات و فهرست از سرور refresh شوند.
- خطای 409 وضعیت قدیمی/transition غیرمجاز را نشان دهد و داده تازه‌سازی شود.
- خطای 403 به‌صورت عدم دسترسی نمایش داده شود؛ دکمه پنهان‌شده جایگزین کنترل سمت سرور نیست.
- timeout/قطع ارتباط نتیجه نامشخص است؛ ارسال دوباره کور ممنوع و ابتدا وضعیت سفارش دوباره دریافت شود.

## 7. حالت‌ها و خطاها

- Loading: skeleton ساده و پایدار برای فهرست و جزئیات.
- Empty: پیام کوتاه، توضیح فیلترهای فعال و اقدام پاک‌کردن فیلتر.
- No results: تفاوت با حالت بدون سفارش اولیه روشن باشد.
- Network error: حفظ فیلترها و امکان تلاش مجدد امن.
- Invalid filter/date: پیام نزدیک کنترل مربوط.
- Permission denied: نمایش عدم دسترسی بدون افشای داده خارج از scope.
- Order not found: سفارش حذف‌شده/شناسه نامعتبر/خارج از شعبه به‌صورت پیام عمومی امن؛ جزئیات بین شعبه‌ها افشا نشود.
- Feature disabled: اگر entitlement مرکز سفارش غیرفعال است، دسترسی صفحه و API هر دو باید کنترل شوند؛ صرف مخفی‌کردن منو کافی نیست.
- Partial data: فیلد اختیاری ناموجود با متن جایگزین نمایش داده شود؛ داده جعلی ساخته نشود.

## 8. واکنش‌گرایی و دسترس‌پذیری

- دسکتاپ: فهرست با ستون‌های محدود و خوانا؛ جزئیات در صفحه مستقل یا پنل عریض.
- تبلت: جدول به ردیف‌های کارتی با دو وضعیت مستقل تبدیل شود.
- موبایل: هر سفارش یک کارت با شماره، زمان، مبلغ و دو وضعیت؛ فیلترها در drawer تمام‌عرض.
- RTL کامل؛ شماره سفارش، UUID، تلفن و شناسه‌های فنی در قطعه LTR جداگانه.
- وضعیت‌ها علاوه بر رنگ با متن و آیکون/نشانه قابل تشخیص باشند.
- کنتراست، فوکوس صفحه‌کلید، target لمسی و برچسب فرم رعایت شود.
- برند ثابت «Powered by PersiaCoder.ir» مطابق پوسته عمومی محصول حفظ شود.

## 9. قرارداد داده و وابستگی‌ها

### قرارداد فهرست موجود
- فیلترهای status، channel، payment status، fulfillment method، from/to date.
- پاسخ شامل سفارش‌ها، `has_more` و `next_cursor`.
- هر ردیف: شناسه عمومی، شماره، کانال، وضعیت سفارش، وضعیت پرداخت، زیرجمع، مالیات، کل، واحد پول، زمان ثبت، روش دریافت و مشتری.
- scope کسب‌وکار/شعبه سمت Backend اعمال می‌شود.

### قرارداد جزئیات موجود
- سفارش، اقلام و گزینه‌ها، fulfillment/customer snapshot و تاریخچه وضعیت.
- تاریخچه رویداد فقط status event است.
- اطلاعات پرداخت تراکنشی/refund در این پاسخ وجود ندارد.

### موارد نیازمند تکمیل API یا بررسی بیشتر
1. جست‌وجوی server-side بر اساس شماره سفارش، نام/شماره مشتری.
2. شمارش کل نتایج و badgeهای تجمیعی، اگر نیاز محصولی تأیید شود.
3. تاریخچه پرداخت، receipt و refund با مرجع تراکنش و مبالغ واقعی ledger.
4. قرارداد eventهای انبار، پیامک، آماده‌سازی و تحویل برای timeline ترکیبی.
5. بررسی دقیق کنترل مجوز برای همه انتقال‌های وضعیت و routeهای متناظر.
6. همسان‌سازی مقدار وضعیت پرداخت `partial` در فهرست مجاز با شرط لغو در کد که `partially_paid` را بررسی می‌کند؛ این ناسازگاری باید در فاز Backend/Payment اصلاح و تست شود، نه با workaround در UI.

## 10. معیار پذیرش طراحی

- [ ] فهرست، همه کانال‌های پشتیبانی‌شده را از یک API و با scope شعبه نمایش می‌دهد.
- [ ] فیلترهای موجود با مقادیر مجاز Backend منطبق‌اند.
- [ ] cursor و فیلتر تاریخ محلی timezone کسب‌وکار را رعایت می‌کنند.
- [ ] وضعیت سفارش و پرداخت در فهرست و جزئیات مستقل‌اند.
- [ ] اقلام و افزودنی‌ها از snapshot سفارش خوانده می‌شوند.
- [ ] timeline فقط status eventهای واقعی را نمایش می‌دهد.
- [ ] اقدامات فقط مطابق state machine و مجوز واقعی سرور قابل اجرا هستند.
- [ ] لغو/رد دارای دلیل است و با refund اشتباه نمی‌شود.
- [ ] timeout و خطای شبکه باعث ایجاد transition تکراری نمی‌شوند.
- [ ] UI برای loading، empty، no results، error، permission و feature-disabled طراحی شده است.
- [ ] دسکتاپ، تبلت، موبایل و RTL پوشش داده شده‌اند.
- [ ] اطلاعات مالی/پرداختی که API ارائه نمی‌کند، جعل یا از وضعیت کلی استنتاج نمی‌شود.

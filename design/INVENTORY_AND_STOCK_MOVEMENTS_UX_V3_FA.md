## 1. هدف و قواعد پایه

یک نقطه روشن برای پاسخ به چهار سؤال:
- چه ماده‌ای داریم؟
- در کدام انبارک/مکان قرار دارد؟
- چه مقدار فیزیکی، رزروشده و قابل استفاده است؟
- چه سندی باعث تغییر مانده شده است؟

اصول:
- منبع حقیقت مقدار موجودی، `pos_stock_balances` و گردش، `pos_stock_ledger` است؛ تغییر دستی مستقیم از UI ممنوع.
- هر تغییر موجودی از سند رسمی و posting سمت سرور انجام شود.
- داده‌ها در scope کسب‌وکار و شعبه محدود بمانند.
- مقادیر مقداری با precision اعشاری نگهداری شوند؛ فرمت UI مطابق واحد و decimal_places باشد.
- واحد پایه Stock Item بعد از ایجاد تغییرپذیر نیست.
- سیاست موجودی منفی فعلی فقط `block` است.
- posting سند باید idempotent و transaction-safe باشد؛ کلیک مجدد نباید اثر تکراری ایجاد کند.
- برند و UX فارسی/RTL و مینیمال حفظ شود.

## 2. ساختار صفحه انبار

ناوبری پیشنهادی:
1. نمای کلی موجودی
2. مواد اولیه
3. انبارک‌ها / مکان‌ها
4. اسناد انبار
5. گردش موجودی (ledger)
6. تأمین‌کنندگان
7. واحدها (فهرست مرجع؛ مدیریت واحد فقط در صورت API مدیریتی جداگانه)

صفحه موجود `InventoryWorkspace` اکنون این داده‌ها را از API دریافت می‌کند: stock items، locations، balances، ledger، units، documents و suppliers. طراحی جدید باید قابلیت‌های فعلی را منظم‌تر کند و منبع داده موازی نسازد.

## 3. داشبورد موجودی

### شاخص‌ها
- تعداد مواد اولیه فعال.
- مجموع موجودی فیزیکی.
- مجموع رزروشده.
- مجموع قابل استفاده.

نکته: جمع مقدارهای واحدهای ناهمگون (مثلاً کیلوگرم + لیتر + عدد) از نظر بُعد فیزیکی معنی ندارد. UI نباید یک «جمع کل» واحد از واحدهای متفاوت نشان دهد. شاخص‌های موجود باید بر اساس dimension/واحد تفکیک شوند یا فقط تعداد/تعداد اقلام را نمایش دهند. این مورد برای اصلاح نمایش فعلی مهم است.

### فهرست مانده
- ماده اولیه، کد، واحد پایه.
- مکان/انبارک.
- موجودی فیزیکی `quantity_on_hand`.
- رزروشده `quantity_reserved`.
- قابل استفاده `quantity_available`.
- زمان آخرین به‌روزرسانی.

فیلترها: ماده اولیه و مکان. API مانده limit حداکثر 200 دارد و در قرارداد بررسی‌شده cursor ندارد؛ بارگذاری بیشتر سروری نباید بدون API اضافه نمایش داده شود.

## 4. مواد اولیه / Stock Items

### فهرست و فرم
- کد، نام، واحد پایه، وضعیت فعال.
- جست‌وجو بر اساس نام یا کد؛ limit حداکثر 100.
- واحد پایه از فهرست مرجع واحدها انتخاب شود.
- dimension واحد باید در فرم واضح باشد.
- بعد از ایجاد، تغییر واحد پایه ممنوع است؛ در حالت ویرایش فیلد read-only و دلیل آن نمایش داده شود.
- کد در scope کسب‌وکار یکتا است.
- سیاست منفی موجودی فقط `block`؛ کنترل انتخابی برای سیاست‌های دیگر نمایش داده نشود.
- غیرفعال‌سازی ماده‌ای که موجودی مانده یا در رسپی فعال استفاده شده باشد با conflict رد می‌شود.
- غیرفعال‌سازی، حذف تاریخی یا حذف ledger نیست.

## 5. واحدها و تبدیل

- فهرست واحدها شامل code، name، dimension و decimal_places است.
- مقدارهای مجاز در اسناد می‌توانند واحدی متفاوت از واحد پایه داشته باشند، مشروط به dimension یکسان و وجود conversion factor معتبر.
- سرویس در زمان افزودن ردیف سند، dimension را تطبیق می‌دهد و conversion factor را snapshot می‌کند.
- مقدار واردشده در UI در واحد انتخابی نمایش داده شود؛ مقدار پایه فقط در جزئیات/valuation به‌عنوان مقدار تبدیل‌شده نمایش داده شود.
- تبدیل بین dimensionهای متفاوت ممنوع است.
- تعریف/ویرایش conversion factor و مدیریت مرجع واحدها در UI فعلی مشخص نشده؛ تا وجود API مدیریتی، فقط انتخاب واحدها و تبدیل‌های از قبل تعریف‌شده ارائه شود.

## 6. انبارک‌ها / Stock Locations

- هر مکان متعلق به کسب‌وکار و شعبه مشخص است.
- فیلدها: کد، نام، نوع مکان، وضعیت فعال.
- نوع‌های موجود: `storage`، `kitchen`، `bar`، `freezer`، `other`.
- کد در همان شعبه یکتا است.
- مکان دارای موجودی فیزیکی یا رزروشده قابل غیرفعال‌سازی نیست.
- انتقال سند فقط بین دو مکان متفاوت از همان شعبه است.
- انتخاب شعبه و scope آن باید از BusinessScope معتبر بیاید؛ UI اجازه ارسال شناسه شعبه دلخواه خارج از مجوز را نمی‌دهد.

## 7. تأمین‌کنندگان

- فهرست تأمین‌کننده با نام، تلفن، یادداشت و وضعیت فعال.
- ایجاد و ویرایش؛ غیرفعال‌سازی به‌جای حذف.
- رسید خرید به تأمین‌کننده فعال نیاز دارد.
- تأمین‌کننده در سند به‌عنوان مرجع خرید snapshot/relationship نمایش داده شود؛ تغییر بعدی اطلاعات تماس نباید سند تاریخی را بازنویسی کند.
- شماره تماس و یادداشت فقط برای نقش‌های مجاز نمایش داده شوند.

## 8. اسناد انبار

### انواع ثبت‌شده در سرویس
- `purchase_receipt`: رسید خرید.
- `consumption`: مصرف.
- `transfer`: انتقال.
- `adjustment_in`: تعدیل افزایشی.
- `adjustment_out`: تعدیل کاهشی.
- `waste`: ضایعات.
- `return`: برگشت.

وضعیت سند: `draft`، `posted`، `voided`. در مسیر فعلی، ایجاد و ویرایش draft و posting برای انواع مشخص موجود است؛ عملیات void در controller/service بررسی‌شده مشاهده نشد و نباید دکمه باطل‌سازی عملیاتی نمایش داده شود.

### ساخت سند
گام 1 — مشخصات:
- نوع سند.
- مکان مبدأ.
- مکان مقصد فقط برای انتقال.
- تأمین‌کننده فقط برای رسید خرید.
- دلیل اجباری برای تعدیل افزایشی، تعدیل کاهشی و ضایعات.

گام 2 — ردیف‌ها:
- ماده اولیه.
- مقدار مثبت اعشاری تا 6 رقم اعشار.
- واحد هم‌بُعد با واحد پایه.
- مبلغ کل به تومان برای رسید خرید و تعدیل افزایشی اجباری.
- یادداشت اختیاری.
- امکان افزودن چند ردیف به پیش‌نویس.
- ویرایش و حذف ردیف فقط در draft.

گام 3 — بازبینی:
- شماره سند.
- نوع، مبدأ/مقصد، تأمین‌کننده، دلیل.
- ردیف‌ها، مقدار تبدیل‌شده به واحد پایه و مبلغ/ارزش در صورت وجود.
- هشدار روشن: «ثبت نهایی، مانده و ledger را تغییر می‌دهد».

گام 4 — ثبت نهایی:
- دکمه اصلی فقط برای سند draft غیرخالی و قابل posting.
- هنگام درخواست، قفل کنترل و نمایش progress.
- پس از موفقیت، refresh سند، مانده و ledger.
- timeout: سند را دوباره نساز و posting را کور تکرار نکن؛ ابتدا وضعیت سند را استعلام کن. Idempotency key باید برای همان عملیات ثابت بماند.

### قواعد posting اثبات‌شده
- فقط draft قابل posting است.
- سند باید حداقل یک ردیف داشته باشد.
- تأمین‌کننده رسید خرید هنگام posting باید هنوز فعال باشد.
- انواع postable در کد: purchase_receipt، transfer، adjustment_in، adjustment_out، consumption، waste.
- نوع `return` فعلاً قابل posting نیست؛ سرویس خطای صریح می‌دهد چون سیاست ارزش‌گذاری و پیوند به سند مبدأ هنوز فعال نشده است.
- مکان مبدأ/مقصد باید معتبر و فعال باشد.
- posting از balance با قفل ردیف `FOR UPDATE` استفاده می‌کند.
- خروجی موجودی، موجودی قابل استفاده (on-hand منهای reserved) را کنترل می‌کند و موجودی منفی/برداشت از مقدار رزروشده را نمی‌پذیرد.
- ledger برای هر حرکت با مقدار، نوع حرکت، هزینه snapshot و source event key ثبت می‌شود.
- رسید خرید/ورودی هزینه، میانگین موزون هزینه را به‌روزرسانی می‌کند.
- انتقال باید اثر خروج و ورود متقابل و ثبت ledger در دو مکان داشته باشد.
- ثبت نهایی و تغییر موجودی باید در یک transaction واحد باشند؛ جزئیات دقیق transaction boundary در posting service باید در تست پایان فاز بررسی شود.

## 9. فهرست اسناد و جزئیات

فهرست:
- شماره سند، نوع، وضعیت، مبدأ/مقصد، تأمین‌کننده، تاریخ ایجاد/ثبت.
- فیلتر نوع و وضعیت.
- limit حداکثر 100.
- API فهرست جاری در این بررسی cursor را نشان نمی‌دهد؛ UI باید مطابق limit موجود رفتار کند.

جزئیات:
- سربرگ و وضعیت سند.
- خطوط و مقدار در واحد انتخابی و base quantity.
- conversion factor snapshot.
- unit cost snapshot و total cost در صورت موجود بودن.
- دلیل و اطلاعات مرجع.
- زمان ایجاد و posted_at.
- عملیات ویرایش/حذف خط فقط در draft.
- در posted، همه فیلدهای سند read-only؛ اصلاح باید با سند اصلاحی مجاز و policy روشن انجام شود، نه ویرایش تاریخچه.

## 10. Valuation و هزینه

- سرویس valuation جزئیات خطوط سند، base_quantity، unit_cost_snapshot و total_cost_amount را برمی‌گرداند.
- ورود موجودی از رسید خرید/تعدیل افزایشی مبلغ کل را به تومان دریافت می‌کند.
- posting repository محاسبه هزینه واحد و میانگین موزون را با decimal انجام می‌دهد.
- خروج موجودی از average_unit_cost موجود برای snapshot هزینه استفاده می‌کند.
- UI مبلغ را تومان نشان دهد و از تبدیل پنهان ریال/تومان اجتناب کند.
- سود، بهای تمام‌شده محصول و گزارش حسابداری رسمی از این صفحه استنتاج نشود؛ صحت مدل ارزش‌گذاری باید با تست مالی و نمونه‌های واقعی پذیرفته شود.

## 11. Ledger / گردش موجودی

هر ردیف:
- زمان.
- ماده اولیه و کد.
- مکان.
- نوع حرکت.
- مقدار مثبت/منفی در واحد پایه.
- شماره و نوع سند مرتبط، در صورت وجود.
- یادداشت.
- هزینه snapshot در صورت API.

فهرست از جدید به قدیم و cursor با `before_id` است؛ limit بین 1 تا 100. Ledger append-only تصور شود؛ ویرایش/حذف مستقیم رویداد در UI وجود ندارد. فیلتر ماده و مکان باید cursor را reset کند.

## 12. ارتباط با رسپی و سفارش

- سندهای `consumption` فعلی می‌توانند مصرف مواد را از مسیر رسمی انبار ثبت کنند.
- schema شامل reservation، reservation lines، recipe version، recipe lines و order-item recipe snapshots است.
- در این بررسی، اتصال end-to-end ایجاد سفارش به رزرو، پذیرش/آماده‌سازی به مصرف، لغو به آزادسازی و recipe version به posting خودکار، اثبات نشده است.
- UI نباید با ثبت دستی مصرف، وانمود کند که مصرف سفارش به‌صورت خودکار متصل است.
- تا تعیین policy، نقطه رزرو/مصرف، زمان انقضا، آزادسازی، مکان برداشت و رفتار سفارش نیمه‌تمام باز می‌ماند.

## 13. نقش‌ها، امنیت و خطاها

- همه queryها باید با business + branch scope اجرا شوند.
- عملیات نوشتن دارای actor، idempotency و audit باشند.
- permissionهای دقیق هر route و policy role باید در ممیزی RBAC تطبیق داده شوند؛ این سند مجوزی را حدس نمی‌زند.
- خطاهای مهم:
  - واحد نامعتبر یا dimension ناسازگار.
  - conversion factor مفقود.
  - موجودی قابل استفاده ناکافی.
  - مکان غیرفعال/نامعتبر.
  - تأمین‌کننده غیرفعال.
  - سند غیر draft یا خالی.
  - return not postable.
  - کد تکراری ماده/مکان.
  - تلاش برای غیرفعال‌سازی قلم/مکان دارای مانده یا رزرو.
- در 409 یا timeout، داده تازه شود؛ posting مجدد با کلید جدید ممنوع تا تعیین نتیجه قبلی.
- عدم دسترسی و feature disabled باید در UI و Backend enforce شوند.

## 14. واکنش‌گرایی و حالت‌ها

- موبایل: کارت‌های موجودی، فیلتر drawer و wizard سند تک‌ستونه.

## 15. مغایرت‌ها و کارهای باقی‌مانده

1. مجموع مقدار فیزیکی/قابل استفاده فعلی UI از همه balanceها بدون تفکیک dimension جمع می‌شود؛ جمع واحدهای ناهمگون از نظر فیزیکی بی‌معنی است. UI باید به تفکیک dimension اصلاح شود.
2. در مسیر quick submit فعلی، سند ساخته، یک خط اضافه و سپس post می‌شود. اگر مرحله add/post شکست بخورد، draft باقی می‌ماند؛ UI پیام مناسب می‌دهد، اما مسیر بازیابی و نمایش draftهای ناقص باید روشن باشد.
3. API فهرست سند limit دارد و pagination cursor مشاهده نشد؛ برای حجم بالا باید pagination طراحی شود.
4. نوع return در create/list موجود است اما posting مسدود است؛ UX باید آن را غیرفعال/با توضیح «در حال تکمیل» نشان دهد تا کاربر سندی نسازد که نمی‌تواند نهایی کند.
5. وضعیت voided در مدل داده هست، اما عملیات void در controller/service بررسی‌شده دیده نشد.
6. permissionهای route-level، تست concurrency posting، conversion، average cost و rollback transaction باید در gate فاز 5 اجرا شوند.
7. اتصال خودکار recipe/order/reservation/consumption هنوز نیازمند تکمیل و تست است.
8. سیاست supplier snapshot، اصلاح سند posted و source-linked return باید مشخص شود.

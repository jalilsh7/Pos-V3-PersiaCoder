- وضعیت: **آماده نمونه‌سازی مفهومی؛ نیازمند تکمیل Backend و بازبینی مالک**
- مرجع تصمیمات محصول: `FINAL_PRODUCT_DECISIONS_FA.md`
- وابستگی‌ها: D-07 مرکز سفارش، D-08 کاتالوگ/رسپی، D-09 انبار، D-06 پرداخت/رسید، D-10 مشتری/پیامک.
- مراجع فنی: `StorefrontWorkspace.tsx`، `PosWorkspace.tsx`، `OrderService`، `CatalogService`، `v3/backend/public/index.php` و schema سفارش/پرداخت.

> Storefront فعلی فقط preview مستقل با menu seed و cart محلی است. در routeهای Backend بررسی‌شده endpoint عمومی storefront/checkout مشاهده نشد. سند حاضر تجربه هدف را تعریف می‌کند و به‌هیچ‌وجه ادعای ثبت سفارش آنلاین، پرداخت آنلاین یا کنترل ساعات کاری واقعی ندارد.

## 1. تصمیمات قطعی محصول که باید رعایت شوند

- فروشگاه آنلاین یک قابلیت اصلی V3 و دامنه قطعی فاز 7 است.
- یک قالب عمومی منودار و منعطف برای رستوران، کافه، فست‌فود، آبمیوه‌فروشی، بستنی‌فروشی و کسب‌وکارهای مشابه استفاده می‌شود؛ برای هر صنف یک نرم‌افزار یا موتور سفارش جدا ساخته نشود.
- تفاوت صنف از طریق پروفایل، دسته‌بندی، محصولات، تصاویر، تنوع، افزودنی، محتوا و تنظیمات ظاهر اعمال شود.
- Storefront لایه ارائه عمومی است و از همان Catalog، Pricing، Customer، Orders، Payments و Inventory استفاده می‌کند.
- سفارش آنلاین با channel مشخص در همان مرکز سفارش POS ظاهر می‌شود و به آماده‌سازی/تحویل متصل می‌شود.
- ساعات کاری و باز/بسته بودن فروشگاه از پنل کنترل می‌شود.
- قیمت، موجودی، مالیات و پرداخت در Backend مرجع نهایی دارند.

## 2. وضعیت واقعی موجود

### Frontend
- `StorefrontWorkspace` از آرایه ثابت menuItems، قیمت‌ها و وضعیت availability استفاده می‌کند.
- جست‌وجو، فیلتر دسته، تغییر تعداد و cart فقط state محلی است.
- انتخاب pickup/delivery وجود دارد اما checkout و ثبت سفارش ندارد.
- پیام صریح preview نمایش داده می‌شود و دکمه ادامه سفارش غیرفعال است.
- ساعات کاری با نشان «باز · نمایشی» ثابت شده و از Backend دریافت نمی‌شود.

### Backend
- OrderService موتور مشترک ایجاد سفارش را دارد و source channelهای فعلی را اعتبارسنجی می‌کند.
- APIهای catalog برای محصولات و جزئیات تنوع/گزینه وجود دارند.
- در routeهای جاری بررسی‌شده endpoint عمومی storefront، cart/checkout، دریافت تنظیمات عمومی فروشگاه یا ایجاد سفارش بدون session کاربر پیدا نشد.
- routeهای orders فعلی پشت session و permission هستند؛ این مسیر را نباید بدون طراحی public checkout باز کرد.
- schema پرداخت/fulfillment وجود دارد، اما اتصال end-to-end Storefront→Order→Payment→Fulfillment اثبات نشده است.

## 3. ساختار تجربه مشتری

### صفحه اصلی فروشگاه
- برند/لوگو و نام کسب‌وکار.
- معرفی کوتاه و تصویر کاور.
- وضعیت واقعی باز/بسته و پیام علت تعطیلی در صورت وجود policy.
- دسته‌های منو و جست‌وجو.
- کارت محصول با تصویر، نام، توضیح کوتاه، قیمت از Backend و نشان موجود/ناموجود.
- سبد خرید همیشه قابل دسترسی و خلاصه تعداد/جمع.
- Powered by PersiaCoder.ir مطابق برند ثابت محصول.

### دسته و جست‌وجو
- جست‌وجو روی نام و توضیح قابل نمایش.
- دسته‌ها از کاتالوگ فعال و عمومی دریافت شوند؛ دسته خالی/غیرفعال نمایش داده نشود.
- فیلترهای کلاینتی فقط روی داده کامل دریافت‌شده معتبرند؛ فهرست سروری باید pagination و حد نتایج روشن داشته باشد.
- محتوای SEO و URL دسته/محصول از طراحی قالب عمومی پشتیبانی کند، بدون موتور سفارش مستقل.

### صفحه محصول
- تصویر، نام، توضیح، قیمت پایه، availability.
- تنوع‌ها با اختلاف قیمت.
- گروه افزودنی single/multiple با حداقل/حداکثر و اجباری/اختیاری.
- قیمت نهایی نمایشی از جمع مقادیر Backend یا quote معتبر؛ فرانت‌اند مرجع قیمت نیست.
- افزودن به سبد فقط پس از تکمیل انتخاب‌های اجباری.

## 4. سبد خرید

- هر ردیف شامل محصول، تنوع، گزینه‌های انتخابی، تعداد و قیمت snapshot/quote است.
- دو انتخاب متفاوت از یک محصول (مثلاً تنوع یا افزودنی متفاوت) دو ردیف مستقل‌اند.
- تغییر تعداد، حذف ردیف و پاک‌کردن سبد.
- سبد به session/cart token امن و کوتاه‌عمر متصل شود؛ قیمت/availability در checkout مجدداً سمت سرور اعتبارسنجی شوند.
- تغییر کاتالوگ یا قیمت در فاصله افزودن به سبد تا checkout باید با پیام «قیمت/موجودی به‌روز شد» و دریافت quote تازه مدیریت شود.
- cart local state به‌تنهایی سفارش ثبت‌شده نیست و نباید order number تولید کند.

## 5. روش دریافت و اطلاعات مشتری

روش‌های دریافت فعلی در مدل fulfillment: `dine_in`، `takeaway` و `delivery`. Storefront باید فقط روش‌هایی را نشان دهد که از تنظیمات واقعی کسب‌وکار/شعبه فعال و مجازند.

### دریافت حضوری / pickup
- نام و شماره تماس مشتری بر اساس policy checkout.
- زمان دریافت فقط پس از تعریف API زمان‌بندی و ظرفیت؛ فعلاً زمان‌بندی را فرض نکن.
- پیام تأیید سفارش و شناسه پیگیری.

### ارسال
- نام گیرنده، تلفن معتبر، نشانی، محدوده ارسال و هزینه ارسال.
- محدوده و هزینه باید از Backend و تنظیمات کسب‌وکار بیاید.
- آدرس/تلفن snapshot سفارش باشد.
- اگر آدرس خارج از محدوده است یا ارسال در آن ساعت غیرفعال است، قبل از پرداخت توضیح داده شود.

### مشتری
- امکان سفارش به‌صورت مهمان یا حساب کاربری، تنها پس از تصمیم/قرارداد احراز هویت مشتری.
- اگر مشتری شناخته‌شده است، اتصال به پروفایل و سابقه خرید با رضایت/مجوز مناسب.
- پیامک تراکنشی برای تأیید و تغییر وضعیت؛ پیامک تبلیغاتی فقط با رضایت معتبر و opt-out.
- چک‌باکس رضایت فعال پیش‌فرض، رضایت معتبر ایجاد نمی‌کند.

## 6. ساعات کاری و باز/بسته بودن

- وضعیت open/closed باید از Backend محاسبه شود و timezone مؤثر شعبه را رعایت کند.
- ساعات هفتگی، استثناهای تعطیلی، تعطیلی موقت و override دستی از Business Configuration API خوانده شوند.
- اگر فروشگاه بسته است، policy مصوب مشخص کند سفارش جدید بسته شود، پیش‌سفارش مجاز باشد یا زمان بعدی پیشنهاد شود؛ این policy هنوز نیازمند تکمیل است.
- وضعیت نمایش داده‌شده باید زمان آخرین sync و علت بسته بودن را در صورت وجود نشان دهد.
- ساعت دستگاه مشتری مرجع وضعیت فروشگاه نیست.

## 7. Checkout و قیمت‌گذاری

### مراحل پیشنهادی
1. بازبینی سبد و quote تازه.
2. انتخاب روش دریافت و اعتبارسنجی محدوده/زمان.
3. ورود اطلاعات مشتری و تماس.
4. نمایش زیرجمع، تخفیف، مالیات، هزینه ارسال و مبلغ کل از Backend.
5. انتخاب روش پرداخت فعال.
6. ایجاد سفارش و payment intent/transaction با idempotency.
7. نمایش نتیجه قطعی یا pending/unknown با شناسه پیگیری.

### قواعد
- هرگز مبلغ کل را صرفاً با جمع client cart به‌عنوان مبلغ قطعی اعلام نکن.
- تخفیف، مالیات، هزینه ارسال و availability از سرور.
- سفارش و پرداخت دو state machine مستقل‌اند.
- پرداخت ناموفق یا unknown به‌عنوان فروش تسویه‌شده نشان داده نشود.
- retry پس از timeout باید ابتدا وضعیت payment intent/order را استعلام کند؛ سفارش یا پرداخت تکراری ممنوع.
- callback provider باید امضا/اعتبارسنجی و idempotent باشد.

## 8. اتصال به مرکز سفارش و POS

- سفارش Storefront با channel `storefront` یا مقدار نهایی مصوب واحد ثبت شود؛ enum نهایی باید با OrderService و قرارداد API یکسان شود.
- سفارش در مرکز سفارش مشترک شعبه دیده شود؛ فهرست جداگانه و موتور وضعیت موازی نساز.
- order item، variant، option و قیمت snapshot شوند.
- customer/fulfillment/address snapshot به سفارش متصل شوند.
- آشپزخانه و تحویل از همان order ID استفاده کنند.
- خطا در SMS یا provider جانبی نباید سفارش ثبت‌شده را حذف یا rollback کند.
- سفارش آنلاین بدون payment موفق/روش مجاز باید مطابق policy order/payment state مدیریت شود؛ وضعیت «پرداخت‌شده» جعل نشود.

## 9. پرداخت و رسید

- روش‌های پرداخت storefront از Payment API و تنظیمات مجاز نصب دریافت شوند.
- درگاه آنلاین از پرداخت نقدی/کارتخوان POS جداست.
- redirect به provider با state/nonce امن و callback سرور.
- وضعیت pending، authorized، captured، failed، cancelled، unknown و refund بر اساس state machine واقعی.
- رسید شامل شماره سفارش، اقلام، مبالغ، روش پرداخت و شناسه پیگیری؛ اطلاعات کارت حساس ذخیره/نمایش داده نشود.
- رسید مشتری و رسید آشپزخانه/تحویل دو خروجی مجزا هستند.

یک قالب پایه مشترک با بخش‌های قابل پیکربندی:
- رنگ و لوگو در محدوده Design System و برند ثابت PersiaCoder.ir.
- تصویر کاور، معرفی و اطلاعات تماس.
- دسته‌بندی و ترتیب نمایش.
- تصاویر محصول و توضیح.
- تنوع و افزودنی.
- ساعات کاری و روش‌های دریافت.
- بنر/اطلاعیه تعطیلی و حداقل اطلاعات عمومی.

از ساخت چند storefront جدا با داده/سفارش مستقل خودداری شود. White-label و حذف برند PersiaCoder.ir مجاز نیست.

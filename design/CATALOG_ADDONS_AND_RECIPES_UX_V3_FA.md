# طراحی UX کاتالوگ، افزودنی و رسپی — PersiaCoder POS V3

- شناسه: DESIGN-CATALOG-RECIPE-2026-001
- نسخه: 0.1
- تاریخ: 2026-11-20
- بسته: D-08
- وضعیت: **آماده نمونه‌سازی کاتالوگ؛ بخش رسپی نیازمند تکمیل قرارداد Backend و بازبینی مالک**
- مرجع تصمیمات: `FINAL_PRODUCT_DECISIONS_FA.md`
- مراجع کد بررسی‌شده: `v3/backend/src/Catalog/CatalogService.php`، `v3/backend/src/Infrastructure/Database/CatalogRepository.php`، `v3/backend/src/Inventory/InventoryService.php`، `v3/backend/src/Infrastructure/Database/InventoryRepository.php` و `database/v3/schema.sql`

> این سند UX و نقشه قابلیت‌هاست، نه اعلام تکمیل UI یا چرخه رسپی. در HEAD بررسی‌شده، APIهای کاتالوگ برای دسته، محصول، تنوع و گروه/گزینه وجود دارند. ساختار داده رسپی و نسخه‌ها در schema دیده می‌شود، اما در مسیرهای سرویس بررسی‌شده، RecipeService یا CRUD عملیاتی نسخه رسپی پیدا نشد. تا زمان اثبات endpoint و تست واقعی، رسپی «زیرساخت داده/نیازمند تکمیل» است.

## 1. هدف و اصول

مدیریت ساده و سریع منو و مواد اولیه برای کسب‌وکار غذا و نوشیدنی؛ اطلاعاتی که در POS و فروشگاه آنلاین نمایش داده می‌شود باید از یک کاتالوگ مشترک تغذیه شود.

- کاتالوگ مرجع نام، دسته، SKU، نوع محصول، قیمت پایه، نرخ مالیات، تنوع و گزینه‌های انتخابی است.
- انبار مرجع مواد اولیه، واحد پایه، مکان و موجودی است؛ کالا/محصول فروش با ماده اولیه یکی فرض نمی‌شود.
- یک محصول می‌تواند بدون رسپی فروخته شود؛ وضعیت رسپی باید شفاف و قابل تشخیص باشد، نه اینکه برای هر محصول به‌اجبار رسپی فرض شود.
- داده سفارش تاریخی snapshot است؛ تغییر کاتالوگ یا رسپی جاری نباید سفارش‌های قبلی را بازنویسی کند.
- ظاهر مینیمال، شیک، فارسی، RTL و مناسب کار با صفحه لمسی؛ جزئیات پیشرفته در بخش‌های ثانویه.
- قیمت و مالیات نهایی فقط توسط Backend محاسبه و اعتبارسنجی می‌شوند.
- غیرفعال‌کردن یا آرشیو، حذف داده تاریخی نیست.

## 2. نقشه ناوبری پیشنهادی

زیرمنوی «کاتالوگ و منو»:
1. دسته‌بندی‌ها
2. محصولات
3. گروه‌های افزودنی
4. رسپی‌ها (تا زمان آماده‌شدن API با وضعیت «در حال تکمیل» و بدون فرم عملیاتی)
5. مواد اولیه و واحدها (پیوند به ماژول انبار؛ منبع داده تکراری نساز)

صفحه اصلی کاتالوگ با تب/فیلتر سبک بین محصولات و دسته‌ها؛ گروه‌های افزودنی در بخش مدیریت مستقل نگهداری شوند تا یک گروه قابل استفاده مجدد باشد.

## 3. دسته‌بندی‌ها

### فهرست
- نام، دسته والد، ترتیب نمایش، فعال/غیرفعال و تصویر در صورت اتصال media.
- دسته‌های تو در تو از `parent_id` پشتیبانی می‌کنند؛ عمق نامحدود در UI فرض نشود تا محدودیت چرخه/عمق در API بررسی شود.
- مرتب‌سازی با `sort_order` و سپس نام.
- فیلتر فعال/غیرفعال در UI؛ فهرست API فعلی هر دو وضعیت را برمی‌گرداند.

### ایجاد/ویرایش
- نام الزامی، حداکثر 120 کاراکتر در سرویس create/update.
- دسته والد اختیاری؛ انتخاب والد باید فقط دسته همان کسب‌وکار باشد.
- ترتیب نمایش عددی.
- وضعیت فعال.
- تصویر فقط وقتی upload/attach API و مجوز media در دسترس است؛ schema رابطه media دارد اما قرارداد کامل مدیریت رسانه در این بسته تأیید نشده است.

### قواعد
- حذف سخت از UI ارائه نشود؛ دسته محصول‌دار باید با سیاست امن غیرفعال/انتقال مدیریت شود.
- کنترل جلوگیری از چرخه والد باید سمت Backend تضمین شود؛ در سرویس فعلی self-parent رد می‌شود، ولی بررسی کامل جلوگیری از ancestor cycle باید جداگانه تست/تکمیل شود.
- تغییر نام/ترتیب دسته روی سفارش تاریخی اثر ندارد.

## 4. محصولات

### فهرست محصولات
ستون‌ها/کارت‌ها:
- نام و تصویر (در صورت وجود)
- SKU
- دسته
- نوع محصول
- قیمت پایه
- نرخ مالیات
- وضعیت فعال
- نشانگر وجود تنوع/افزودنی در صورت دریافت از جزئیات یا projection معتبر

فیلترها: جست‌وجوی نام/SKU، دسته و وضعیت. API فعلی `listProducts` جست‌وجو و category و limit را می‌پذیرد؛ limit بین 1 تا 100. صفحه‌بندی cursor در این قرارداد فهرست مشاهده نشده؛ UI نباید صفحه‌بندی سروری جعلی بسازد.

### فرم ایجاد/ویرایش
- نام: الزامی، حداکثر 180 کاراکتر.
- SKU: اختیاری؛ حداکثر 80 کاراکتر از حروف لاتین، عدد، نقطه، خط تیره و underscore؛ یکتایی در دامنه‌ای که DB enforce می‌کند بررسی شود.
- نوع محصول: `prepared`، `packaged`، `ingredient` یا `service`.
- قیمت پایه: عدد صحیح نامنفی در واحد پول داخلی schema (تومان).
- نرخ مالیات: basis points از 0 تا 10000؛ در UI درصد قابل فهم نمایش داده شود و تبدیل دقیق به bps انجام شود.
- دسته: اختیاری؛ باید متعلق به همان کسب‌وکار باشد.
- وضعیت فعال/غیرفعال.
- ایجاد و ویرایش با idempotency و audit در سرویس موجود انجام می‌شود.
- آرشیو محصول به‌صورت soft archive با `archived_at` انجام می‌شود؛ دکمه حذف دائمی نمایش داده نشود.

### تجربه ویرایش
فرم به بخش‌های کوتاه تقسیم شود:
1. اطلاعات اصلی
2. قیمت و مالیات
3. تنوع‌ها
4. افزودنی‌ها
5. رسپی و مواد اولیه (در صورت پشتیبانی واقعی)
6. وضعیت و سوابق

در نسخه اولیه، تب‌های فاقد API نباید فرم فعال یا دکمه ذخیره نمایشی داشته باشند.

## 5. تنوع محصول (Variants)

- هر تنوع متعلق به یک محصول است.
- فیلدهای فعلی: نام، SKU اختیاری، `price_delta_amount` و فعال/غیرفعال.
- اختلاف قیمت می‌تواند مثبت یا منفی باشد؛ قیمت نهایی باید در Backend کنترل شود تا منفی یا خارج از محدوده نشود.
- SKU تنوع در دامنه محصول یکتا بررسی می‌شود.
- فهرست جزئیات محصول، تنوع‌ها را همراه جزئیات برمی‌گرداند.
- ساختار فعلی تنوع‌ها به‌صورت delta نسبت به قیمت پایه است؛ مدل چندقیمتی مستقل/واحد فروش/بارکدهای متعدد را به آن نسبت نده.
- مثال UX: «کوچک»، «متوسط»، «بزرگ»؛ این مثال صرفاً داده نمایشی است و مقدار/قیمت واقعی را تعیین نمی‌کند.

## 6. گروه‌های افزودنی و گزینه‌ها

### مدل داده واقعی
- گروه افزودنی دارای نام، نوع انتخاب `single|multiple`، `min_select`، `max_select`، `is_required_default` و وضعیت فعال است.
- هر گروه یک یا چند گزینه دارد؛ گزینه دارای نام، `price_delta_amount` و وضعیت فعال است.
- گروه به محصول با رابطه مستقل متصل می‌شود؛ اتصال دارای `sort_order` و `is_required` است.
- یک گروه می‌تواند بین چند محصول استفاده مجدد شود.
- API ایجاد گروه در حال حاضر 1 تا 100 گزینه می‌پذیرد؛ max_select نباید از تعداد گزینه‌ها بیشتر باشد و single حداکثر یک انتخاب دارد.
- ویرایش گروه تعداد گزینه‌های فعال را با min/max کنترل می‌کند.
- غیرفعال‌سازی گزینه‌ای که حداقل/حداکثر انتخاب گروه را نقض کند رد می‌شود.
- گروه تکراری برای یک محصول با خطای conflict رد می‌شود.

### UX ساخت گروه
- نام گروه، نوع انتخاب، حداقل و حداکثر انتخاب، الزامی‌بودن پیش‌فرض.
- لیست گزینه‌ها با نام و اختلاف قیمت؛ امکان افزودن ردیف و مرتب‌سازی در UI تنها در صورت پشتیبانی endpoint.
- اعتبارسنجی فوری min/max و تعداد گزینه‌ها؛ خطای نهایی Backend همچنان مرجع است.
- مثال‌ها: نوع نان، میزان تندی، افزودنی پنیر یا سس؛ صرفاً نمونه UX.

### اتصال به محصول
- انتخاب گروه موجود از فهرست.
- تعیین ترتیب نمایش و `is_required` برای همین محصول.
- نشان‌دادن تفاوت «الزام پیش‌فرض گروه» و «الزام اتصال گروه به محصول»؛ این دو مقدار در مدل فعلی جدا هستند.
- اتصال مجدد گروه به همان محصول با پیام «از قبل متصل است».
- حذف رابطه فقط پس از وجود endpoint واقعی؛ در کد بررسی‌شده عملیات attach تأیید شد، detach در سرویس دیده نشد.

### انتخاب افزودنی در POS
- فقط گروه‌های فعال و گزینه‌های فعال قابل انتخاب باشند.
- حداقل/حداکثر و نوع انتخاب در UI رعایت شود؛ Backend هنگام ایجاد سفارش باید عضویت گزینه در گروه محصول، فعال بودن و bounds را دوباره بررسی کند.
- قیمت delta از سرور معتبر باشد؛ کلاینت مبلغ نهایی را مرجع قرار ندهد.
- سفارش، نام گروه و گزینه و اختلاف قیمت را snapshot می‌کند؛ تغییرات بعدی کاتالوگ نباید رسید/جزئیات سفارش قبلی را عوض کند.

## 7. مواد اولیه و واحدها (اتصال به Inventory)

### تفکیک موجودیت‌ها
- محصول فروش: آیتم منو/کاتالوگ مانند قهوه یا ساندویچ.
- ماده اولیه/Stock Item: موجودی قابل شمارش مانند دانه قهوه، شیر، نان یا بسته‌بندی.
- واحد پایه هر ماده در زمان ایجاد انتخاب می‌شود و در سرویس فعلی پس از ایجاد immutable است.
- واحدها از فهرست مرجع `pos_units` می‌آیند و شامل کد، نام، dimension و decimal_places هستند.
- انواع مکان انبار در سرویس فعلی: `storage`، `kitchen`، `bar`، `freezer`، `other`.
- سیاست منفی موجودی فعلی فقط `block` را پشتیبانی می‌کند؛ گزینه دیگری در UI ارائه نشود.

### مدیریت مواد اولیه
- کد، نام، واحد پایه و وضعیت فعال.
- کد در محدوده کسب‌وکار یکتا.
- ماده‌ای که موجودی مانده یا در رسپی فعال استفاده شده باشد، طبق سرویس فعلی قابل غیرفعال‌سازی نیست.
- موجودی و گردش از ماژول انبار نمایش داده شود؛ مقدار موجودی در فرم کاتالوگ منبع حقیقت جداگانه نداشته باشد.
- محل نگهداری، موجودی و ledger در صفحات انبار مدیریت می‌شوند؛ کاتالوگ فقط در صورت نیاز خلاصه read-only ارائه کند.

## 8. رسپی و نسخه‌بندی

### آنچه schema فعلی اثبات می‌کند
- `pos_recipes`: ارتباط محصول و در صورت نیاز variant با نام و وضعیت فعال.
- `pos_recipe_versions`: شماره نسخه یکتا در هر رسپی، وضعیت `draft|active|retired`، `effective_from` و ایجادکننده.
- `pos_recipe_lines`: ماده اولیه، مقدار، واحد، conversion factor snapshot و درصد ضایعات.
- `pos_order_items.recipe_version_id`: ارجاع ردیف سفارش به نسخه رسپی.
- `pos_order_item_recipe_lines`: snapshot مقدار موردنیاز، مقدار مصرف‌شده، هزینه واحد snapshot و مکان برای هر ماده.
- این ساختار برای حفظ تاریخچه و محاسبه مصرف/بهای مواد طراحی شده؛ وجود schema به معنی پیاده‌سازی سرویس، API یا posting نیست.

### UX هدف پس از تکمیل Backend
1. فهرست رسپی‌های محصول/تنوع با نسخه فعال و وضعیت.
2. ساخت نسخه draft جدید بدون بازنویسی نسخه فعال قبلی.
3. افزودن ماده اولیه از فهرست Stock Item و انتخاب واحد سازگار.
4. مقدار مصرف، ضریب تبدیل snapshot و درصد ضایعات.
5. پیش‌نمایش مواد موردنیاز برای مقدار تولید/فروش نمونه؛ محاسبه نهایی باید سمت سرور باشد.
6. اعتبارسنجی سازگاری dimension واحد و conversion factor مثبت.
7. فعال‌سازی نسخه جدید با تاریخ اثرگذاری و ثبت actor؛ نسخه قبلی طبق policy به retired منتقل شود، مشروط به رفتار واقعی API.
8. نمایش تاریخچه نسخه‌ها و عدم تغییر recipe_version_id سفارش‌های تاریخی.

### مواردی که نباید حدس زده شوند
- آیا برای هر محصول چند رسپی فعال مجاز است یا فقط یک نسخه فعال در هر محصول/تنوع؟
- سیاست fallback وقتی محصول رسپی ندارد.
- نقطه رزرو مواد و نقطه مصرف (ثبت سفارش، پذیرش، شروع آماده‌سازی یا تکمیل).
- منبع location برای مصرف، اولویت چند انبار و انتقال بین شعب.
- فرمول گردکردن مقدار، واحدهای قابل تبدیل و ضایعات.
- نحوه برخورد با تغییر رسپی در سفارش باز یا سفارش پرداخت‌شده.
- زمان و روش ثبت هزینه واحد snapshot و valuation.
- بازگشت موجودی در لغو/مرجوعی و میزان مواد قابل برگشت.
این‌ها موضوعات باز محصول/عملیات‌اند؛ سند تصمیمات محصول آن‌ها را قطعی نکرده است.

## 9. Snapshot و سفارش تاریخی

- نام محصول، تنوع، SKU، مقدار، قیمت واحد، تخفیف، نرخ/مبلغ مالیات و جمع ردیف در `pos_order_items` snapshot می‌شوند.
- گزینه‌های انتخاب‌شده با نام گروه/گزینه و delta قیمت snapshot در `pos_order_item_options` ثبت می‌شوند.
- شناسه‌های محصول/تنوع/گزینه برای ردیابی به‌صورت nullable نگهداری می‌شوند و snapshot متنی مستقل است.
- نسخه رسپی در سطح ردیف سفارش reference می‌شود؛ خطوط مواد/مقدار/هزینه نیز جدول snapshot اختصاصی دارند.
- تغییر نام، قیمت، مالیات، تنوع، گزینه یا رسپی جاری نباید سفارش تاریخی را دوباره قیمت‌گذاری کند.
- هر صفحه جزئیات سفارش باید snapshot را نشان دهد؛ پیوند به محصول جاری صرفاً برای مشاهده اطلاعات فعلی و با برچسب روشن باشد.

## 10. رسانه و تصاویر

- فهرست دسته/محصول از طریق رابطه media در repository می‌تواند تصویر متصل را نمایش دهد و URL API رسانه را برگرداند.
- در این بسته قرارداد کامل upload، crop، حذف امن، محدودیت MIME/اندازه، storage و مجوز رسانه بررسی نشده است.
- تا تکمیل قرارداد رسانه، UI از placeholder استفاده کند و آپلود نمایشی/ذخیره محلی را به‌عنوان قابلیت پایدار ارائه ندهد.
- تصاویر باید برای کارت POS بهینه و نسبت تصویر یکسان داشته باشند؛ نبود تصویر نباید چیدمان را بشکند.

## 11. مجوز، audit و امنیت

- عملیات نوشتن کاتالوگ در سرویس با actor، BusinessScope، idempotency و audit طراحی شده‌اند.
- هر endpoint باید مجوز دقیق خود را در transport/controller یا service اعمال کند؛ وجود audit/idempotency به‌تنهایی اثبات RBAC نیست.
- scope کسب‌وکار باید در تمام repository queryها اعمال شود؛ ID داخلی از کلاینت دریافت نشود.
- قیمت، مالیات، SKU و ارتباط گروه/گزینه در سرور اعتبارسنجی شود.
- برای ایجاد/ویرایش، idempotency key پایدار ارسال شود؛ retry بعد از timeout بدون استعلام نتیجه نباید duplicate بسازد.
- غیرفعال‌سازی، archive و تغییر رسپی باید با audit قابل پیگیری باشد.

## 12. حالت‌های UI و واکنش‌گرایی

- Loading: skeleton مختصر.
- Empty: پیام روشن و اقدام «افزودن اولین محصول/دسته».
- Search no result: حفظ عبارت و پاک‌کردن فیلتر.
- Validation: خطای نزدیک فیلد + خطای سرور با کد قابل ردیابی.
- Conflict: SKU تکراری، گروه متصل، bounds ناسازگار یا ماده اولیه در حال استفاده.
- Network/timeout: حفظ فرم و عدم ارسال کور؛ نتیجه عملیات با idempotency استعلام شود.
- Permission denied / feature disabled: عدم دسترسی با کنترل سمت سرور؛ منو پنهان‌سازی به‌تنهایی کافی نیست.
- دسکتاپ: فهرست جدولی و فرم با بخش‌های مشخص.
- تبلت: فهرست کارتی و پنل ویرایش تمام‌عرض.
- موبایل: کارت محصول، فیلتر drawer و فرم تک‌ستونه.
- RTL کامل؛ SKU و شناسه‌های فنی در قطعه LTR؛ کنترل‌های لمسی مناسب.

## 13. قراردادها و کارهای تکمیلی Backend

1. فهرست/CRUD گروه‌های افزودنی و گزینه‌ها: endpoint list/details و pagination/filter را کامل و مستند کن؛ جزئیات محصول گروه‌های متصل را برمی‌گرداند.
2. عملیات detach گروه از محصول و مرتب‌سازی گروه/گزینه‌ها در صورت نیاز محصول.
3. جلوگیری از چرخه دسته‌بندی و آزمون race در SKU یکتا.
4. تضمین اعتبارسنجی گروه/گزینه‌های انتخابی و قیمت delta هنگام ساخت سفارش.
5. endpointهای رسانه و کنترل امنیت فایل.
6. API کامل Recipe/RecipeVersion/RecipeLine: list, detail, draft, update, activate, retire با transaction، audit و idempotency.
7. تضمین قواعد version concurrency و یکتایی نسخه فعال مطابق policy مصوب.
8. قرارداد واحد و conversion بر اساس dimension و ثبت conversion snapshot.
9. integration بین recipe version، order item، reservation، consumption و stock ledger.
10. تفکیک دسترسی Catalog write، Recipe write و Inventory write در RBAC.

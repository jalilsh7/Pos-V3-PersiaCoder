# طراحی UX انبار، مکان‌ها، موجودی و اسناد گردش کالا — PersiaCoder POS V3

- شناسه: DESIGN-INVENTORY-WORKSPACE-2026-001
- نسخه: 0.1
- تاریخ: 2026-11-20
- بسته بک‌لاگ: D-09
- وضعیت: **آماده نمونه‌سازی؛ نیازمند بازبینی مالک**
- مرجع تصمیمات محصول: `FINAL_PRODUCT_DECISIONS_FA.md`
- مراجع فنی: `InventoryService`، `InventoryDocumentService`، `InventoryPostingService`، `InventoryRepository`، `InventoryDocumentRepository`، `InventoryPostingRepository`، `InventoryController`، `database/v3/schema.sql` و migrationهای 011 و 012.
- مرجع UI: `InventoryWorkspace.tsx` و `client.ts`.

> این سند UX موجودی و اسناد فعلی را توصیف می‌کند؛ زمان رزرو/مصرف خودکار مواد بر اساس سفارش را تعیین نمی‌کند. اسناد موجود قابلیت‌های مشخصی دارند، اما نوع «return» در Backend فعلی قابل posting نیست و نباید به‌عنوان گردش برگشت عملیاتی نمایش داده شود.

## 1. هدف و اصول

مرکز انبار باید به مدیر کمک کند مقدار واقعی هر ماده را در هر مکان شعبه بفهمد، گردش‌ها را ردیابی کند و با سندهای قابل ممیزی موجودی را تغییر دهد.

- اقلام انبار، واحد پایه، مکان، مانده، ledger و اسناد از API واقعی دریافت شوند.
- هر تغییر موجودی از مسیر سند و posting انجام شود؛ ویرایش مستقیم مانده در UI وجود نداشته باشد.
- موجودی on-hand، reserved و available جدا نمایش داده شوند.
- business/branch scope و مجوزهای Backend مرجع دسترسی‌اند.
- ثبت سند در draft موجودی را تغییر نمی‌دهد؛ فقط posting سند اثر موجودی را اعمال می‌کند.
- سند posted نباید مانند draft قابل ویرایش باشد؛ اصلاح باید طبق قرارداد سند اصلاحی/گردش مجاز انجام شود.
- رابط فارسی، RTL، مینیمال و قابل استفاده با لمس باشد.

## 2. ساختار اطلاعات

تب‌های اصلی:
1. نمای کلی موجودی
2. اقلام انبار
3. مکان‌ها / انبارک‌ها
4. اسناد انبار
5. گردش موجودی (ledger)
6. تأمین‌کنندگان

### نمای کلی
- خلاصه تعداد اقلام فعال، مکان‌های فعال و کمبودها فقط وقتی API محاسبه معتبر ارائه کند.
- جدول موجودی با قلم، کد، واحد پایه، مکان، on-hand، reserved، available و زمان آخرین تغییر.
- فیلتر قلم، مکان و جست‌وجوی نام/کد.
- هیچ badge «کمبود» یا «در حال اتمام» بدون threshold مصوب نمایش داده نشود.

## 3. اقلام انبار و واحدها

### قلم انبار
- code، name، base unit، active flag.
- کد در محدوده کسب‌وکار یکتا است.
- واحد پایه هنگام ایجاد انتخاب می‌شود؛ API ویرایش فعلی code/name/is_active را تغییر می‌دهد و واحد پایه را تغییر نمی‌دهد.
- اقلام دارای مانده یا رسپی فعال، نباید بدون policy پاک‌سازی/انتقال حذف شوند؛ UI فقط فعال/غیرفعال را مدیریت کند.
- policy فعلی ایجاد قلم فقط `block` برای موجودی منفی را قبول می‌کند؛ گزینه‌های policy دیگر ارائه نشوند.
- جست‌وجو بر اساس نام و code، سقف پاسخ API برابر limit حداکثر 100 است؛ UI نباید یک صفحه محدود را کل اقلام فرض کند.

### واحدها و تبدیل
- فهرست واحدها از API مرجع با code، name، dimension و decimal precision دریافت می‌شود.
- انتخاب واحدهای رسپی/سند فقط در dimension سازگار با ماده مجاز باشد.
- conversion factor باید از رکورد معتبر و effective زمان درخواست به دست آید و در خط سند/رسپی snapshot شود.
- اگر تبدیل وجود ندارد یا نامعتبر است، ذخیره متوقف و خطای روشن نمایش داده شود.
- واحدها/تبدیل‌های استاندارد reference data مشترک‌اند؛ UI مدیریت آزاد واحد مرجع را در scope مشتری نمایش ندهد.

## 4. مکان‌ها / انبارک‌ها

- مکان در محدوده business و branch تعریف می‌شود.
- کد، نام، نوع مکان و active flag نمایش داده شود.
- انواع مجاز باید دقیقاً از enum قرارداد Backend خوانده شوند؛ مقدار پیش‌فرض UI به‌تنهایی enum کامل را تعیین نمی‌کند.
- انتقال بین مکان‌ها فقط با سند `transfer` و انتخاب مبدأ/مقصد متفاوت در همان شعبه.
- مکان دارای موجودی on-hand یا reserved نباید به‌گونه‌ای غیرفعال شود که گردش/گزارش تاریخی نامفهوم گردد؛ Backend مانع غیرفعال‌سازی ناسازگار را اعمال می‌کند.
- مکان غیرفعال در اسناد جدید قابل انتخاب نیست.

## 5. موجودی و ledger

### مانده‌ها
برای هر قلم/مکان:
- `quantity_on_hand`: مقدار موجود فیزیکی/دفترکل.
- `quantity_reserved`: مقدار رزروشده.
- `quantity_available`: on-hand منهای reserved.
- واحد پایه و زمان به‌روزرسانی.

مقادیر decimal باید با precision واقعی نمایش داده شوند؛ تبدیل به integer یا گردکردن پنهانی ممنوع است.

### گردش
- ledger به ترتیب جدیدترین شناسه و با cursor `before_id` صفحه‌بندی می‌شود.
- نوع حرکت، مقدار delta، ماده، مکان، سند مرتبط، شماره سند، یادداشت و زمان نمایش داده شود.
- ledger مرجع audit گردش است؛ ردیف‌ها و اثرهای تاریخی را در UI ویرایش نکن.
- انتقال یک سند می‌تواند حرکت خروجی و ورودی داشته باشد؛ در رابط، دو طرف انتقال با همان سند مرتبط و قابل دنبال‌کردن باشند.

## 6. اسناد انبار

### انواع سند موجود در سرویس
- `purchase_receipt`: رسید خرید؛ تأمین‌کننده اجباری و بهای کل هر خط الزامی.
- `consumption`: مصرف.
- `transfer`: انتقال؛ مکان مقصد متفاوت اجباری.
- `adjustment_in`: تعدیل افزایشی؛ دلیل و بهای کل خط الزامی.
- `adjustment_out`: تعدیل کاهشی؛ دلیل اجباری.
- `waste`: ضایعات؛ دلیل اجباری.
- `return`: نوع سند در create/list وجود دارد، اما posting آن فعلاً با خطای «نیازمند policy برگشت متصل به منبع و valuation» متوقف می‌شود.

### چرخه سند
1. ایجاد سند draft با نوع، مکان، مقصد/تأمین‌کننده و دلیل متناسب.
2. افزودن/ویرایش/حذف خطوط فقط در draft.
3. بررسی جزئیات، واحد، تبدیل، مقدار و بهای کل (در صورت الزام).
4. مشاهده valuation برای نقش مجاز و نوع‌های پشتیبانی‌شده.
5. posting با idempotency key.
6. نمایش نتیجه قطعی، refresh مانده‌ها و ledger.

- سند باید حداقل یک خط داشته باشد تا post شود.
- مقدار هر خط مثبت است و تا 6 رقم اعشار پشتیبانی می‌شود.
- خطوط فقط از stock item فعال همان business انتخاب می‌شوند.
- purchase_receipt به supplier فعال نیاز دارد.
- فقط نوع‌های پشتیبانی‌شده در posting قابل ثبت نهایی‌اند.
- درخواست تکراری باید با idempotency مدیریت شود؛ UI پس از timeout ابتدا وضعیت سند را استعلام کند و post کور تکرار نشود.
- سند posted در فرم draft باز نشود؛ عملیات اصلاحی باید از سند جدید و ledger انجام شود.

### نمایش مبلغ و valuation
- سرویس فعلی valuation، currency برابر `TOMAN` برمی‌گرداند.
- بهای کل برای purchase_receipt و adjustment_in الزامی است؛ برای سایر انواع در ورودی مجاز نیست.
- valuation فقط برای نقش مجاز `inventory.manage` route شده است.
- روش valuation موجود در کد را بدون بررسی کامل posting/repository به‌عنوان سیاست نهایی کل محصول معرفی نکن؛ سند UI فقط خروجی API را نمایش دهد.

## 7. تأمین‌کنندگان

- فهرست، ایجاد و ویرایش تأمین‌کننده از API وجود دارد.
- نام، تلفن، یادداشت و وضعیت فعال در UI مدیریت شود؛ داده حساس/اختیاری فقط در صورت بازگشت API نمایش داده شود.
- تأمین‌کننده غیرفعال در رسید خرید جدید انتخاب نشود.
- رسید خرید ثبت‌شده باید snapshot/مرجع تاریخی تأمین‌کننده را حفظ کند.

## 8. ارتباط با رسپی و سفارش

- رسپی، مواد و مقادیر مصرفی را تعریف می‌کند؛ انبار، مانده و ledger را نگه می‌دارد.
- سند `consumption` در حال حاضر یک سند انبار مستقل است.
- وجود `pos_stock_reservations` و FK به سفارش در schema به معنی فعال‌بودن رزرو خودکار سفارش نیست.
- OrderService در ممیزی جداگانه باید از نظر ثبت recipe_version_id و فراخوانی posting بررسی شود.
- زمان رزرو، زمان مصرف، محل برداشت، آزادسازی رزرو و اثر لغو/refund همچنان تصمیم‌های باز محصول‌اند؛ UX دکمه یا جریان خودکار برای آن‌ها جعل نکند.
- مصرف مواد با سند دستی نباید به‌عنوان مصرف خودکار سفارش معرفی شود.

## 9. نقش‌ها و امنیت

- routeهای خواندن و مدیریت از مجوزهای `inventory.read` و `inventory.manage` استفاده می‌کنند؛ بعضی مسیرها branch context لازم دارند.
- دکمه‌ها بر اساس مجوزهای قابل دریافت UI نمایش داده شوند؛ Backend مرجع نهایی است.
- ایجاد/ویرایش/post با CSRF/origin middleware و idempotency در مسیرهای write انجام می‌شود.
- خطای 403، 404 خارج از scope، 409 سند غیر draft/مکان غیرفعال/تعارض و 422 داده نامعتبر باید قابل فهم نمایش داده شوند.
- audit eventهای واقعی Backend منبع تاریخچه‌اند؛ UI نباید actor/time ساختگی بسازد.

## 10. حالت‌ها و واکنش‌گرایی

- Loading مجزا برای مانده، ledger، سند و جزئیات.
- Empty برای نبود قلم/مکان/سند/گردش.
- Error با حفظ داده فرم draft.
- سند draft قابل ویرایش و posted فقط خواندنی.
- سند return غیرقابل post با توضیح «قابلیت ثبت نهایی هنوز فعال نیست»؛ بهتر است تا زمان پیاده‌سازی policy اصلاً در اقدام سریع سندهای قابل ثبت قرار نگیرد.
- دسکتاپ: جدول موجودی و ledger با ستون‌های ضروری.
- تبلت: ردیف‌های کارتی و عملیات لمسی.
- موبایل: کارت قلم/مکان و کارت سند؛ فرم چندمرحله‌ای/بخش‌بندی‌شده.
- RTL و کد/UUID/مقدارهای فنی با جهت صحیح.

## 11. موارد باز و شکاف‌های فنی

### تصمیم محصولی باز
1. policy رزرو و مصرف اتوماتیک سفارش/رسپی.
2. سیاست موجودی منفی در سطح کسب‌وکار/شعبه/قلم (کد فعلی فقط block).
3. valuation نهایی و روش بهای تمام‌شده.
4. policy برگشت کالا/مواد و ارتباط آن با سند منبع.
5. زمان و مجوز void/reversal اسناد posted.
6. حد هشدار کمبود و replenishment.
7. چندانبار/انتقال بین شعبه و مرزهای آن.
8. نحوه محاسبه هزینه ضایعات و اثر مالی آن.

### شکاف فنی
1. UI فعلی load اولیه از limit ثابت می‌گیرد؛ pagination کامل برای اقلام، مانده و اسناد باید ارزیابی شود.
2. endpointهای فهرست مانده و اسناد محدود به limit هستند؛ UX نباید مجموع کل را از این صفحات استنتاج کند.
3. قرارداد API برای document return باید تا زمان source-linked valuation غیرفعال بماند یا صریحاً non-postable باشد.
4. بررسی race condition posting و رزرو هم‌زمان، deadlock و isolation روی MySQL/MariaDB.
5. تست‌های integration برای تمام document typeها، conversion snapshot، هزینه، موجودی منفی، انتقال دوطرفه و idempotency.
6. مسیر مصرف سفارش/رسپی و رزرو موجودی هنوز end-to-end اثبات نشده است.
7. مجوز مشاهده valuation و سطح جزئیات هزینه باید با سیاست نقش‌ها بازبینی شود.
